## 1. 뼈대

### 1-1. Kotlin — 배치 계산

**문제.** 역 621개 × 시간대 115 × 방향 2 = 142,830회의 그래프 탐색을 오프라인에서 돌려야 한다.
매달 다시 돌리므로 몇 시간짜리면 곤란하다.

**후보.** Python(생태계·개발속도) / Kotlin·Java(JVM 성능) / Rust(최고 성능)

**선택: Kotlin.**

**근거.**
1. **성능이 실제로 필요했다.** 142,830회 탐색이 Python이면 분 단위로 넘어간다. 실측 2.3초.
2. **이 프로젝트의 부차 목표가 백엔드 이직**이고, 목표 회사들의 서버 언어가 Kotlin/Java다.
   Rust로 더 빠르게 만들 수 있었겠지만 그건 이 프로젝트가 증명하려는 것이 아니다.
3. 널 안정성과 데이터 클래스가 파서·모델 코드를 짧게 만든다. GML·XML 파싱이 코드의 큰 부분이다.

**버린 이유.** Python은 성능도 문제지만, 실거래가 XML 33만 건 파싱에서 차이가 더 크게 났을 것이다.
Rust는 이 규모에 과하다 — JVM으로 2.3초면 최적화할 대상이 없다.

**실측.** 그래프 로드 + 시간표 합성 326,796편 + 탐색 142,830회 = **2.3초**, RSS 500MB 남짓.

### 1-2. TypeScript + Vite — 웹

**문제.** 슬라이더를 움직일 때마다 등시선을 다시 그려야 한다. 도달시간 벡터 → 격자 → 컨투어가
매번 도는데, 여기서 버벅이면 제품이 죽는다.

**선택: TypeScript, 프레임워크 없음, Vite 번들.**

**근거.**
1. **상태가 단순하다.** 출발역·시각·예산·방종류·전월세·조건 — 10개 남짓의 평면 상태다.
   React를 넣으면 리렌더 최적화라는 없던 문제가 생긴다.
2. 형변환 실수가 곧 지도 오류가 된다. `[lon, lat]` 과 `LatLng(lat, lng)` 를 섞으면
   조용히 다른 나라를 가리킨다. 타입이 이걸 잡아준다.
3. Vite는 dev 서버 HMR이 즉시라 지도 작업의 반복 속도가 빠르다.

**실측.** 슬라이더 조작 → 재렌더 **128~413ms**(12회 측정, 중앙값 304ms). 예산이 클수록
격자가 넓어져 선형으로 는다. 상태가 평면이라 리렌더 최적화가 필요한 지점이 없었다.

## 2. 아키텍처

### 2-1. 오프라인 배치 + 정적 파일 — 서버 코드 0줄

**문제.** 통근 도달권을 보여주려면 경로탐색이 필요하다. 보통은 라우팅 엔진(OTP2·R5)을
서버에 띄우고 API로 부른다.

**선택: 런타임 라우팅 없음. 전부 미리 계산해 정적 파일로 뿌린다.**

**근거.** **입력 공간이 작다.** 출발지가 임의의 좌표가 아니라 **전철역 621개**다.
시간대도 운행시간 10분 단위 115개 × 방향 2개뿐이다. 조합이 142,830개면 전부 미리 계산할 수 있다.

라우팅 엔진은 "출발지가 임의의 좌표"일 때 필요한 물건이다. 우리 문제는 그렇지 않은데
엔진을 띄우면 **운영 부담만 생기고 얻는 게 없다** — JVM 상주, 메모리, 장애 지점, 배포.

**버린 이유.** 서버를 두면 포트폴리오에 "서버 운영 경험"이 생긴다는 유혹이 있었다.
하지만 필요 없는 서버를 띄운 것 자체가 판단 실패로 읽힌다고 봤다.

**실측.** 서버 코드 **0줄**. 운영 비용 0원. 가동률은 GitHub Pages가 책임진다.

### 2-2. threshold를 계산에서 뺀다 — uint8 도달시간 벡터

**문제.** "40분 도달권"을 미리 그려 두면 사용자가 50분으로 바꿀 때 다시 받아야 한다.
시간 슬라이더가 있는 제품에서 이건 치명적이다.

**후보.** 예산별 폴리곤 미리 생성 / 도달시간 벡터 저장 후 클라이언트 필터

**선택: 벡터 저장.** 역마다 "각 목적지 역까지 몇 분"을 uint8 배열로 저장한다. 255는 도달 불가.

**근거.** threshold는 **표시의 문제지 계산의 문제가 아니다.** 계산 결과에서 분리하면
슬라이더가 네트워크를 안 탄다. 예산 10~120분을 5분 단위로 미리 만들었다면 23배가 됐을 것이다.

`uint8` 인 이유는 도달시간이 분 단위로 255분이면 충분해서다. `int` 면 4배다.

**실측.** 역당 **144KB**, 전체 88MB. 슬라이더 → 재렌더 128~413ms, **네트워크 호출 0회**.
이 결정 하나가 뒤에서 두 번 더 값을 했다 — 동네 필터와 건물 필터가 폴리곤 검사 없이
같은 벡터를 O(1)로 찍어보면 끝난다.

### 2-3. 시간 의존 Dijkstra — RAPTOR 대신

**문제.** 대중교통 경로탐색은 시간 의존적이다. 08:00 출발과 23:00 출발의 도달권이 다르다.
표준 알고리즘은 RAPTOR(Microsoft Research, 2012)로, 태생적으로 1:N이라 도달권에 적합하다.

**선택: 시간 의존 Dijkstra.**

**근거.** **노드가 741개다.** (역, 노선) 쌍으로 만들어도 그렇다.
741개 노드와 그 간선은 **CPU 캐시에 통째로 들어간다.** RAPTOR가 이기는 지점은 캐시 미스와
메모리 대역폭인데, 그게 병목이 아니면 이길 대상이 없다.

우선순위 큐를 `(시각 << 20 | 플랫폼)` 으로 패킹해 롱 하나로 다루면 객체 할당도 사라진다.

**버린 이유.** RAPTOR는 구현이 복잡하고 라운드 기반이라 디버깅이 어렵다.
2.3초로 끝나는 문제에 그 복잡도를 살 이유가 없었다.

**언제 재검토하나.** 버스를 넣으면 노드가 741 → 15만이 된다. 그때는 캐시 논리가 깨지므로
RAPTOR가 **처음으로 의미 있어진다.** 지금 안 쓴 것과 그때 쓰는 것은 모순이 아니다.

**실측.** 탐색 1회 평균 **16µs**. 142,830회 2.3초.

---

### 2-4. 합성 시간표 — 배차간격에서 만든다

**문제.** 실제 시간표를 상시 갱신되는 형태로 구할 수 없다. KTDB GTFS는 2023-03 기준이고,
TAGO는 시간표가 아니라 도착예정정보를 준다.

**선택: 시간대별 배차간격 표에서 출발시각을 생성한다. 단, 탐색은 진짜 시간표만 안다.**

**근거.** "평균 대기 = 배차/2" 같은 근사를 탐색에 섞으면 환승이 얽힐 때 오차가 누적된다.
대신 **배차간격으로 출발시각 목록을 만들어 두고, 탐색은 그것을 진짜 시간표처럼 읽는다.**
근사는 데이터 생성 단계에 가두고 알고리즘은 정확하게 유지한다.

핵심 함정은 **위상(phase)** 이었다. 노선 시작점 기준으로만 배차를 맞추면 중간역의 출발시각이
실제와 어긋난다. 누적 소요시간을 배차로 나눈 나머지를 위상으로 잡아 역마다 정렬해야 한다.
이걸 안 하면 강남 08:00 출발이 한 정거장에 7분으로 나온다.

**실측.** 편성 326,796편 생성. 카카오맵 대조 편향 **−0.9분**.

### 2-5. 격자 + marching squares — 원 union 대신

**문제.** 도달 가능한 역마다 도보 반경 원을 그려 합치면 등시선처럼 보인다. 처음엔 그렇게 했다.

**왜 실패했나.** 원을 반투명으로 겹치면 **겹친 개수만큼 진해진다.** 색이 "몇 분"이 아니라
"원이 몇 개 겹쳤나"를 말하게 된다. 역이 밀집한 도심이 무조건 진해진다.

**선택: 스칼라 필드 → marching squares(`@turf/isobands`).**

역마다 도달시간을 격자에 흩뿌리되 **최솟값을 취하고**(scatter-min), 6회 평활한 뒤
등치선을 뽑는다. 값이 하나뿐이라 겹침 문제가 원천적으로 없다.

**부수 효과가 컸다.** 이 격자가 남아 있어서 동네·건물이 도달권 안인지 판정할 때
point-in-polygon이 필요 없다. 좌표 → 격자 인덱스는 산술 두 번이라 **O(1)** 이고,
6만 건을 매 렌더마다 훑어도 사람이 못 느낀다.

**실측.** 등시선 6구간 생성 포함 128~413ms. 건물 6.2만 건 필터가 그 안에 들어간다.

### 2-6. 어댑터 두 개 — 지도와 데이터

**문제.** 배경지도를 MapLibre에서 카카오맵으로 바꿔야 했다(한글 지명·국내 사용자 친숙도).
카카오는 타일 URL이 아니라 자체 SDK라 MapLibre에 꽂을 수 없다.

**선택: `MapAdapter` 인터페이스.** `setBands` / `setStations` / `setDongs` / `setComplexes` /
`fitBounds` / `onZoom` 만 노출한다. 데이터 쪽에도 같은 이유로 `ReachabilityProvider` 를 뒀다.

**근거.** 배경지도가 바뀐다고 도달권 계산과 UI 코드를 다시 쓸 이유가 없다.
실제로 카카오 SDK가 403(서비스 미활성)·401(도메인 미등록)으로 세 번 막혔는데,
그때마다 **MapLibre로 자동 폴백**해서 화면이 죽지 않았다.

**실측.** 지도 교체 시 `main.ts` 변경 **0줄**. 어댑터 2개 922줄로 격리.

## 3. 쓰지 않기로 한 것

### 3-1. R5 / OTP2 (오픈소스 라우팅 엔진)

**왜 후보였나.** 대중교통 도달권의 표준 도구다. GTFS를 넣으면 바로 동작한다.

**왜 안 썼나.** [2-1](#2-1-오프라인-배치--정적-파일--서버-코드-0줄)과 같은 이유다.
출발지가 621개로 유한하면 엔진이 하는 일을 미리 다 해둘 수 있다.
엔진은 상주 프로세스·메모리·장애 지점을 데려온다.

여기에 더해 실무적 이유가 있었다. **작업량의 대부분은 엔진이 아니라 GTFS 정규화**다.
KTDB 자료는 ID가 비표준인 파일럿이고, 그걸 다듬는 데 드는 시간이 우리가 직접 짠 탐색기보다 크다.

**언제 재검토하나.** 도보 경로가 직선거리로 부족해질 때(한강·산). 그때는 OSM 도보망이
필요하고, 엔진을 쓰는 게 나을 수 있다.

### 3-2. RAPTOR

[2-3](#2-3-시간-의존-dijkstra--raptor-대신)에 적었다. 741 노드에서는 최적화할 대상이 없다.
버스를 넣어 15만 노드가 되면 재검토한다.

### 3-3. 데이터베이스

**왜 후보였나.** 실거래가 33만 건, 건물 6.2만 동, 동 1,768개. 보통 DB에 넣는 규모다.

**왜 안 썼나.** **읽기만 하고, 쓰기가 없고, 질의가 하나뿐이다.**
"도달권 안 + 예산 안"을 찾는 게 전부인데 그건 격자 O(1) 조회로 끝난다.
DB를 두면 인덱스·커넥션·마이그레이션·백업이 따라오는데 그중 무엇도 이 문제를 더 잘 풀지 않는다.

집계 중간 산출물은 JSONL과 JSON으로 둔다. `grep` 과 `python -c` 로 들여다볼 수 있다는 게
디버깅에서 실제로 여러 번 도움이 됐다 — "상봉동 원룸이 1.2억/29만"이라는 이상값을
발견한 것도 파일을 직접 열어봤기 때문이다.

**언제 재검토하나.** 버스 정류장 5만 개의 **도보 환승 간선**을 만들 때. 반경 400m 공간
조인은 전용 인덱스가 있어야 하고, 그건 PostGIS가 표준이다. 그때는 DB가 문제를 실제로 푼다.

---

### 3-4. Kubernetes

**왜 후보였나.** 목표 회사들의 인프라 표준이다.

**왜 안 썼나.** **노드가 하나면 스케줄러가 할 일이 없다.**
배치가 2.3초로 끝나고, 산출물은 정적 파일이며, 상주 프로세스가 없다.
파드로 감쌀 대상 자체가 없다.

억지로 올릴 수는 있다. 하지만 그 순간 [2-1](#2-1-오프라인-배치--정적-파일--서버-코드-0줄)에서
"서버를 억지로 만들지 않는다"고 적은 판단과 정면으로 모순된다.
**설명할 수 없는 기술을 넣는 것보다 안 넣은 이유를 설명하는 쪽이 낫다고 봤다.**

**언제 재검토하나.** 버스를 넣으면 28,000회 Dijkstra가 2시간짜리 배치가 된다.
그걸 여러 워커로 쪼개는 건 K8s Job의 정확한 용례다. 다만 **노드가 하나면 그때도 스레드풀이 답**이고,
쿠버네티스는 노드가 둘 이상일 때 의미가 생긴다. 그 경계를 아는 것이 도입보다 중요하다고 본다.

---

### 3-5. Kafka

**왜 안 썼나.** 배치가 월 1회다. 단계 사이에 큐가 필요 없고 파일로 충분하다.
큐는 **생산과 소비의 속도가 다를 때** 필요한데, 우리는 단계가 순차적이고 각 단계가 끝나야 다음이 시작된다.

**언제 재검토하나.** 버스 도착정보를 일주일 샘플링해 실제 배차간격과 구간 소요시간을 뽑기로 하면,
정류장 5만 개를 분 단위로 폴링하게 된다. 초당 수백 건의 스트림이고 유실이 곧 데이터 구멍이라
거기서는 큐가 정당해진다.

---

### 3-6. MSA

**왜 안 썼나.** 서비스가 하나다. 쪼갤 경계가 없다.

수집기·계산기·배포기라는 자연스러운 구분은 있다. 하지만 그건 **배치의 스텝**이지
마이크로서비스가 아니다. 프로세스 경계로 만들면 얻는 것 없이 직렬화·네트워크 실패·
분산 트랜잭션만 생긴다.

---

### 3-7. GoCD

**왜 후보였나.** 파이프라인을 YAML로 Git에 두고 value stream을 시각화한다.

**왜 안 썼나.** GoCD의 강점은 **여러 팀의 파이프라인이 fan-in/fan-out으로 얽힐 때** 나온다.
우리는 단일 리포에 선형 파이프라인 하나라, GitHub Actions로 40초에 끝난다.

다만 **"파이프라인 설정을 코드로 Git에 둔다"는 철학은 그대로 실천한다.**
`.github/workflows/pages.yml` 이 그 역할이다.

---

## 4. 데이터와 인프라

### 4-1. 공공 API — 크롤링하지 않는다

**문제.** 실매물 호가를 보여주려면 직방·네이버를 크롤링해야 한다.

**선택: 공공 실거래가 API만 쓴다. 매물은 갖지 않고 링크로 넘긴다.**

**근거.** 매물 호가에는 공개 API가 없고, 크롤링은 **저작권법상 데이터베이스제작자의 권리**를
침해한다. 포트폴리오 프로젝트가 법적 회색지대 위에 서면 그 자체가 감점이다.

그래서 제품 포지션을 앞단으로 옮겼다 — **매물을 파는 게 아니라 동네를 정해주는 도구.**
제약을 우회한 게 아니라 제약에서 포지션을 도출했다.

---

### 4-2. 원자료 보존 — 손으로 만든 staging

**문제.** 실거래가 수집은 1,386회 요청에 **45분**이 걸린다. 집계 기준을 바꿀 때마다
다시 받으면 하루가 사라진다.

**선택: 거래 원자료를 JSONL로 남기고, 집계는 그것을 다시 읽는다(`--mode reagg`).**

**근거.** 집계 기준은 반드시 바뀐다. 실제로 두 번 바뀌었다
(중위값 짝짓기 → 환산월세 기준, 그리고 보증금 1,000만원 정규화).

**이 결정이 한 번 프로젝트를 구했다.** 수집이 도중에 죽은 적이 있는데
(실행 중에 jar를 다시 빌드해서 `ClassNotFoundException`), 원자료 35.7MB는 이미 쓰인 뒤였다.
45분 재수집 대신 30초 재집계로 복구했다.

**실측.** 45분 → **30초**. 원자료 44MB.

---

### 4-3. 지오코딩 캐시

**문제.** 건물 6.4만 동에 좌표를 붙여야 하는데 카카오 로컬 호출이 건당 100ms 남짓이라 **2시간**이다.

**선택: `aptSeq` 를 키로 캐시하고, 100건마다 중간 저장한다.**

**근거.** 건물 좌표는 변하지 않는다. 다음 배치부터는 신규 건물만 조회하면 된다.
중간 저장은 끊겨도 처음부터 다시 안 하기 위한 것이다.

**실측.** 첫 실행 2시간 → 재실행 **0초**. 성공률 63,932/63,938 = **99.99%**.

---

### 4-4. GitHub Pages + Actions + 릴리스 자산

**문제.** 산출물이 101MB다. git에 넣으면 바이너리라 델타 압축이 안 돼서
월 1회 갱신마다 전체 복사본이 히스토리에 쌓인다.

**선택: 코드는 Pages, 데이터는 릴리스 자산.** Actions가 빌드 시점에 자산을 내려받아 합친다.

**근거.** 릴리스 자산은 히스토리에 안 들어가고 자산당 2GB까지 된다.
`main` 병합이 곧 배포이고, 데이터 갱신은 자산 교체만으로 끝난다.

**실측.** 배포 40초. 데이터 101MB → gzip **12MB**. git 히스토리 증가 0.

---

## 5. 버스를 넣으면 무엇이 필요해지는가

여기 적은 선택들 상당수가 **"지금 규모에서는"** 이라는 조건 위에 서 있다.
버스가 들어오면 그 조건이 깨진다. 미리 적어 둔다.

| 지금 | 버스 이후 | 그래서 필요해지는 것 |
|---|---|---|
| 노드 741 (캐시에 들어감) | **15만** | RAPTOR 재검토, 또는 병렬화 |
| 탐색 142,830회 2.3초 | **28,000회 × 무거워진 1회 = 2시간** | 워커 분산, 진행률 관측 |
| 산출물 88MB (역→역 행렬) | 역→역 행렬이면 **8.2TB** | 역→격자 벡터로 전환, 오브젝트 스토리지 |
| 도보 환승: 역 741개 전수 비교 | 정류장 **5만 개** | 공간 인덱스 (PostGIS) |
| 외부 API 9종, 수집 45분 | API 13종, 수집 수 시간 | 재시작·스킵 가능한 배치 (Spring Batch) |
| 배치 2.3초 | 배치 2시간 | 관측 (Prometheus·Grafana) |

**이 표가 이 문서의 결론이다.** 기술은 규모가 요구할 때 도입한다.
지금 안 쓴 것들은 못 쓰는 게 아니라 **아직 필요하지 않은 것**이고,
그 경계가 어디인지를 아는 것이 이 프로젝트에서 배운 것이다.
