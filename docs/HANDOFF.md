# 출세권 (chulsegwon) — 인수인계

수도권 대중교통 **출퇴근 도달권(isochrone)** 으로 살 곳을 좁히는 도구.

이 문서는 "무엇을 만들었나"보다 **"왜 그렇게 했나"** 를 남기기 위한 것이다.
코드를 읽으면 알 수 있는 건 적게 쓰고, 코드에 안 남는 판단 근거를 적는다.

- 작성 기준: 2026-09-03
- 브랜치: `dev`(개발) → `main`(병합 시 자동 배포)
- 규모: Kotlin 2,275줄 / TypeScript 3,106줄 / 서버 코드 0줄
- 기술 선택의 이유는 [STACK.md](STACK.md) 에 따로 정리했다 — **쓰지 않기로 한 것** 포함

---

## 1. 문제 정의

이사할 때 "출퇴근 N분 안에 닿는 지역"만 보고 싶은데, 기존 서비스(네이버부동산·직방·
호갱노노)는 단지별 조회는 되어도 **지도 전체를 도달권으로 필터링**하지 못한다.
그 빈틈이 이 프로젝트의 자리다.

부차적 목표: 백엔드 이직 포트폴리오. 이게 설계 판단에 실제로 영향을 줬다
(→ [ADR-1](#adr-1-런타임에-라우팅-엔진을-돌리지-않는다), [ADR-7](#adr-7-서버를-억지로-만들지-않는다)).

## 3. 설계 결정 (ADR)

### ADR-1. 런타임에 라우팅 엔진을 돌리지 않는다

**왜.** 입력 공간이 작기 때문이다. 네이버 지도는 임의 출발 × 임의 도착이라 조합이
무한해서 실시간 엔진이 필요하지만, 이 서비스는 다르다.

- 목적지(직장)는 지프 분포로 몰린다 — 강남·여의도·판교·구디·광화문
- 시간대는 운행시간 10분 단위로 잘라도 유한하다
- 전철역은 621개뿐이다

전부 미리 계산해서 정적 파일로 뿌리면 서버가 필요 없다.

**대안을 버린 이유.** OTP2·R5 같은 오픈소스 엔진은 메모리를 10~16GB 먹는데,
그건 **라이브 질의를 받기 위해** 그래프를 통째로 상주시키기 때문이다. 우리는 라이브
질의를 안 받으므로 그 비용을 낼 이유가 없다.

**결과.** 런타임 서버 코드 0줄. 슬라이더를 아무리 움직여도 네트워크 호출 0회.

### ADR-2. threshold 를 계산에서 뺀다

**왜.** "40분 도달권"을 폴리곤으로 미리 그리면 threshold 마다 파일이 따로 필요하다.
저장하는 것을 **"각 지점까지 몇 분"** 벡터로 바꾸면 threshold 는 클라이언트에서
비교 한 번이면 된다.

```
폴리곤 방식:  700역 × 11 threshold × 평균 300KB ≈ 2.3GB
벡터 방식:    700역 × 1개            × 200KB   ≈ 140MB
```

**부수 효과가 더 크다.** 10분 단위를 5분 단위로 바꿔도 데이터 재생성이 필요 없고,
사용자가 "37분"을 입력해도 그냥 동작한다.

---

### ADR-3. RAPTOR 대신 시간 의존 Dijkstra

**왜.** RAPTOR 가 이기는 건 정류장이 수만 개여서 우선순위 큐의 캐시 미스가 문제될
때다. 지하철만이면 노드가 741개뿐이라 그래프가 통째로 CPU 캐시에 들어간다.
**최적화할 대상이 없다.**

**실측.** 142,830회 탐색이 2.3초. 판단이 맞았다.

**언제 뒤집나.** 버스가 들어와 정류장이 5만 개가 되는 시점. 그때는 직접 짜지 말고
R5 로 넘긴다 (→ [열린 항목](#6-열린-항목)).

> 면접 관점에서도 이쪽이 낫다. "RAPTOR 를 구현했다"보다
> **"노드 700개짜리 문제에 RAPTOR 는 과하다고 판단했고, 버스가 들어오는 시점에
> R5 로 넘겼다"** 가 도구를 고를 줄 안다는 뜻이다.

### ADR-4. 그래프 노드는 역이 아니라 (역, 노선)

**왜.** 강남역을 노드 하나로 두면 2호선 ↔ 신분당선 환승 도보 시간이 사라져서
도달권이 낙관적으로 나온다.

```
내부 그래프:  (강남, 2호선) ──환승 도보──> (강남, 신분당선)
출력 행렬:    강남 = 두 노드 중 min
```

환승 도보시간은 두 승강장 사이 실제 거리에서 뽑는다(고정값 3분보다 정확하다).
거리 중앙값이 119m, 최대 872m로 편차가 크다.

**같은 이름 다른 역 함정.** 이름만으로 승강장을 묶으면 5호선 양평역과 경의중앙선
양평역이 합쳐진다 — **53km 떨어진 역이다.** 이름 + 거리(1km 이내)로 묶는다.

---

### ADR-5. 출근 도달권은 시간축을 뒤집어 푼다

**왜.** 출근은 *"09:00까지 강남역 도착"* 이라 **도착시각 기준(arrive-by)** 이고,
퇴근은 *"19:00 강남역 출발"* 이라 출발시각 기준이다. 한쪽만 만들면 출근 도달권이 틀린다.

역방향 탐색을 따로 짜는 대신, 연결 `(A→B, dep, arr)` 을 `(B→A, -arr, -dep)` 로
뒤집은 망에서 **같은 정방향 코드**를 돌린다.

### ADR-6. 합성 시간표를 쓰되, 탐색은 진짜 시간표만 안다

**왜.** 실제 시간표가 없어서 배차간격 추정으로 시간표를 만들었다. 여기서 선택지가
둘이었다.

1. 배차간격을 대기시간으로 근사해 간선 가중치에 녹인다 → **막차·첫차가 표현 안 되고**,
   나중에 실제 GTFS 로 바꿀 때 탐색 코드까지 다시 써야 한다
2. 합성이라도 열차를 실제로 굴린다 → 교체 지점이 `TimetableBuilder` 하나로 끝난다

2를 골랐다. 지금은 추정이지만 **코드는 진짜 시간표를 받을 준비가 되어 있다.**

**여기서 실제로 버그가 나왔다.** 처음엔 열차를 "체인 시작점 출발시각" 기준으로
굴렸는데, 그러면 노선 중간 역이 한참 전 시간대의 배차간격을 물려받는다.
강남역 08:00 인데 06:20 의 6분 배차를 겪어 1정거장에 7분이 걸렸다.
→ 구간마다 그 시각의 배차로 출발을 찍고, 위상을 누적시간 % 배차로 맞춰 해결.
통과 승객은 대기 0, 승차 승객은 그 시각의 실제 배차만큼 대기한다.

### ADR-7. 서버를 억지로 만들지 않는다

정적 파일로 완결되니 "백엔드가 없어 보인다"는 걱정이 있었다. 결론은
**서버를 끼워넣지 말고 배치 파이프라인을 진짜 백엔드 작업으로 만드는 것.**

GTFS 정규화, 대량 병렬 실행, 바이너리 포맷 설계, 무결성 검증이 전부 백엔드다.
그리고 면접에서 *"왜 API 서버를 안 뒀는지"* 를 설명할 수 있으면 서버를 둔 것보다 강하다.

### ADR-8. 생성 데이터는 git 에 넣지 않는다

바이너리는 git 이 델타 압축을 못 한다. 월 1회 89.5MB 를 갱신할 때마다 전체 복사본이
히스토리에 영구히 쌓인다. 소스는 그대로인데 레포만 부푼다.

현재 레포 154KB. 데이터는 `.gitignore`.

---

### ADR-9. 프론트는 `ReachabilityProvider` 만 본다

v1 은 **역→역 행렬**, Level 2(R5)는 **역→격자 벡터**를 낸다. 포맷이 다르므로 프론트가
둘 중 하나에 직접 붙으면 나중에 프론트를 다시 짜야 한다.

```ts
interface ReachabilityProvider {
  reachability(origin, slot): Promise<ReachabilitySet>
}
```

`map/`, `ui/` 는 뒤가 행렬인지 격자인지 모른다.

### ADR-10. 격자 렌더 → 등시선 (2026-08-30)

**처음엔 원**을 겹쳐 그렸다. `fill-opacity < 1` 이라 겹칠수록 진해져서, 색이
"강남까지 몇 분"이 아니라 **"원이 몇 개 겹쳤나"** 를 나타냈다.

**격자로 바꿨다.** 칸마다 최솟값 하나만 남으니 어떤 칸도 두 번 그려지지 않아 겹침이 사라졌다.
하지만 도보 상한을 4분(반경 300m)으로 줄이면 격자 400m 라 **역마다 사각형 한 칸**만
걸려 블록이 흩어진 것처럼 보였다.

**지금은 등시선.** 스칼라 필드를 만들고 `@turf/isobands` 로 구간 폴리곤을 뽑는다.
격자점 사이를 보간하므로 경계가 매끄럽다.

**marching squares 를 직접 안 짠 이유는 구멍 때문이다.** 20분 구간은 10분 구간을
도넛처럼 감싸야 하는데, 안 그러고 겹쳐 그리면 반투명이 겹쳐 색이 다시 무너진다.
안쪽 링을 바깥 링에 배정하는 게 이 알고리즘의 까다로운 부분이고, turf 가 그걸 해준다.

**비용.** 격자 방식 16ms → 등시선 146ms(예산 40분/도보 15분 기준). 슬라이더에
큐 가드가 있어 밀리지는 않는다. 정확한 색이 반응속도보다 중요하다고 봤다.

### ADR-11. 지도 구현을 어댑터로 분리 (2026-08-30)

카카오·네이버는 타일 엔드포인트가 아니라 **자체 JS SDK** 라 MapLibre 에 꽂을 수 없다.
"타일 URL만 교체"가 불가능하므로 지도 구현 자체를 갈아끼울 경계를 만들었다
([ADR-9](#adr-9-프론트는-reachabilityprovider-만-본다) 와 같은 이유).

**카카오로 갈 수 있게 된 결정적 이유는 스무딩이다.** 격자 2,022칸을 카카오
오버레이 객체로 만들면 불가능했겠지만, 등시선 40조각이면 네이티브 `Polygon` 으로
충분하다. 캔버스 오버레이를 직접 만들 계획이 통째로 사라졌다.

카카오에서 걸린 것들:

- **줌 레벨이 정수다.** MapLibre 는 연속값이라 `fitBounds` 에 패딩을 그대로 넘겼는데,
  카카오는 딱 맞는 배율이 없으면 한 단계 밖으로 반올림한다. 여기에 왼쪽 패딩
  340px(가로의 37%)까지 얹으니 한 단계를 더 잃어 **서울을 보려는데 파주~평택**이 나왔다.
  → 작은 여백(24px)으로 배율만 맞추고, 패널 회피는 `panBy` 픽셀 이동으로 분리
- 레벨 방향도 반대다(작을수록 확대). 어댑터에서 흡수
- 역 점은 200개로 제한. MapLibre 는 한 레이어로 GPU 가 그리지만 카카오는 오버레이가
  객체 하나씩이라 300개면 팬·줌이 무거워진다
- 키·제품 설정이 안 되어 있으면 SDK 가 403 을 낸다. 그때 빈 화면을 보여주느니
  MapLibre 로 자동 대체한다 (실제로 `disabled OPEN_MAP_AND_LOCAL service` 로 한 번 겪음)

### ADR-12. 코드는 Pages, 데이터는 릴리스 자산 (2026-08-30)

`main` 에 병합되면 GitHub Actions 가 배포한다. → <https://klaus9267.github.io/chulsegwon/>

**데이터를 어떻게 올리느냐가 유일한 설계 문제였다.** 생성 데이터 89.5MB 는
git 에 없다([ADR-8](#adr-8-생성-데이터는-git-에-넣지-않는다)). 그대로 연결하면
코드만 올라가고 데이터는 통째로 빠져 빈 지도가 뜬다. 선택지는 셋이었다.

| 방식 | 판정 |
|---|---|
| git 에 커밋 | ❌ 월 1회 갱신마다 전체 복사본이 히스토리에 영구 누적 |
| Git LFS | ❌ 무료 대역폭 쿼터가 먼저 죽는다 |
| **릴리스 자산** | ⭐ 히스토리에 안 들어가고 자산당 2GB. gzip 으로 89.5MB → 10MB |

빌드 때 `gh release download` 로 받아서 `web/public/` 에 푼다. 레포는 154KB 로 유지된다.

**호스팅을 Pages 로 고른 이유는 용량이다.** 사이트 상한이 1GB 라 89.5MB 에 10배
여유가 있다. Vercel Hobby 는 업로드 상한이 100MB 라 지금 이미 90% 고, KTDB 데이터가
들어오면 그날 터진다. 대신 Pages 는 무료 계정에서 **공개 레포**를 요구해서 공개로 전환했다.

**막힌 것 둘:**

- 프로젝트 사이트는 `/<repo>/` 하위로 서빙된다. `"/data"` 를 절대경로로 부르면
  배포판에서 404. `import.meta.env.BASE_URL` 을 쓰고 빌드 시 `--base` 를 넘긴다.
  dev 에서는 `"/"` 라 로컬 동작은 그대로다.
- 카카오는 **Referer 도메인**을 검사한다. 콘솔에 등록 안 된 도메인은 401
  `domain mismatched`. ngrok 은 재시작마다 주소가 바뀌어 매번 등록해야 하지만,
  배포 도메인은 한 번만 등록하면 영구히 유효하다.

**데이터 갱신:**

```bash
tar -czf /tmp/data.tgz -C web/public data
gh release upload data-latest /tmp/data.tgz --clobber
```

### ADR-13. 매물을 갖지 않는다 — 포지션을 앞단으로 (2026-08-30)

**매물 호가는 공공 API 가 없고 크롤링은 저작권법상 데이터베이스제작자 권리 침해다.**
그래서 처음부터 매물 없이 가치를 내는 구조로 잡았다. 이건 제약을 받아들인 게 아니라
**포지션 선택**이다.

집 구하는 순서를 보면 자리가 보인다:

```
1. 이사 결정
2. 후보 지역 좁히기   ← 여기가 비어 있다
3. 단지·매물 고르기   ← 네이버부동산이 이미 잘한다
4. 계약
```

2단계는 방어까지 된다. 네이버·직방은 이걸 **안 만든다** — 그들의 지표는 매물 조회수인데
지역을 좁혀주면 조회수가 줄기 때문이다. 구조적으로 그들이 못 하는 일이다.

호갱노노의 무기였던 "실거래가를 지도에" 는 이미 네이버·아실·직방이 다 한다.
그 자리를 다시 노리는 건 의미가 없다.

**그래서 세 가지에 집중한다:**

| | 상태 | 비용 |
|---|---|---|
| 다중 출발지 교집합 (맞벌이) | ✅ 완료 | 0 — 있는 자료구조로 됨 |
| 도달권 × 실거래가 | ⏸ 키 대기 | 공공데이터포털 + VWorld 키 |
| 네이버부동산 핸드오프 | ✅ 완료 | 0 — 링크만 |

**다중 출발지가 우리만 싸게 할 수 있는 것이다.** *"남편 판교, 아내 여의도, 둘 다 40분 안"*
은 남들이 하려면 라우팅을 N번 돌려야 하는데, 우리는 행렬 하나 더 읽고 element-wise max
한 번이면 끝난다. [벡터로 저장한 결정(ADR-2)](#adr-2-threshold-를-계산에서-뺀다)이 만든 우위다.
실측: 강남 단독 336역 → 강남+판교 교집합 149역, 90ms.

**정직하게 — 리텐션이 구조적으로 안 나온다.** 이사는 2~3년에 한 번이고 도달권은 한 번 보면
끝이다. B2C 재방문을 목표로 잡으면 반드시 실패한다. 현실적인 목표는 포트폴리오,
한 번 쓰고 기억되는 도구, 또는 나중에 도달권을 위젯/API 로 제공하는 B2B 쪽이다.

**하지 않기로 한 것:** CP 제휴·중개사 계약으로 매물 확보(콜드스타트 — 트래픽이 있어야
매물을 주는데 매물이 있어야 트래픽이 난다), 커뮤니티·리뷰(호갱노노가 압도적),
실거래가 분석 심화(아실이 더 잘한다).

### ADR-14. 지도의 주인공을 점에서 **동네 시세**로 (2026-08-31)

아파트 단지 16,504개를 점으로 찍었더니 도달권이 안 보였다. 색은 도달 시간을 말하는데
그 위에 점 수백 개가 덮이면 화면이 말하는 게 없어진다.

바꾼 것은 표시 방법만이 아니다. **무엇을 보여줄 것인가**를 바꿨다.

- 건물 단위 중위값은 거래가 두세 건이라 흔들린다. "이 빌라 전세 1.2억"은 그 집이
  얼마였다는 뜻에 가깝지 시세가 아니다
- 반면 "역삼동 원룸 월세 중위 50만"은 1,376건이 받친다
- 자취 타겟이 정말 알고 싶은 것도 개별 건물이 아니라 **이 동네가 얼마인가**다

그래서 동(법정동) 1,768개를 주 데이터로 두고, 지도에는 점이 아니라 **글자**를 얹는다.
값을 읽으려고 클릭할 필요가 없어야 한다.

배율에 따라 층을 나눈다. 광역(카카오 level ≥9)에서는 동 시세만, 시(6~8)에서는 역까지,
동네(≤5)에서는 개별 건물. 각 배율에서 사용자가 하는 질문이 다르기 때문이다.

### ADR-15. 중위값 두 개를 짝지어 만들지 않는다 (2026-08-31)

처음엔 동네별로 보증금 중위값과 월세 중위값을 따로 뽑아 `보증금/월세` 로 붙였다.
상봉동 원룸이 **1.2억 / 29만** 으로 나왔다. 그런 매물은 없다. 반전세 몇 건이 보증금
분포를 끌어올렸고 월세 분포는 그대로였던 것이다.

고친 방식: 환산월세(`월세 + 보증금 × 5.5% ÷ 12`)로 거래를 한 줄로 세우고, **가운데
있는 실제 거래 한 건**의 보증금·월세를 그대로 쓴다.

- 시장에 존재했던 조합이라 사용자가 그 숫자로 매물을 찾을 수 있다
- 전월세전환율은 지역·시기마다 다르지만, 금액을 맞추려는 게 아니라 **정렬 기준**이라
  고정값으로 충분하다

교훈은 일반적이다. **주변부 통계를 각각 요약해 합치면 존재하지 않는 개체가 만들어진다.**
합쳐야 할 때는 개체를 먼저 고르고 그 개체의 값을 읽어야 한다.

### ADR-16. 편의시설은 아이콘이 아니라 필터 (2026-08-31)

직방·네이버는 편의시설을 지도 위 아이콘으로 보여준다. 아이콘은 켜고 끄는 것이지
거르는 게 아니라서 "편의점 없는 동네를 지워달라"에는 답하지 못한다.

우리는 동마다 반경 800m 안 개수를 세어 두고(카카오 Local 카테고리) **조건으로** 쓴다.
후보가 200개 동네일 때 다음 질문이 "그중 살 만한 데는 어디냐"이고, 자취에서 그건
대부분 생활 인프라라서다.

기준값은 코드에 박지 않고 **분포의 상위 40% 지점**에서 뽑는다. "편의점 15개 이상"이
많은 건지는 다른 동네와 비교해야 알 수 있고, 반경이나 수집 시점이 바뀌면 박아둔 숫자는
곧 거짓말이 된다. 비교 모집단은 **후보가 될 수 있는 동네**(원룸 거래 100건 이상)로
좁힌다. 연천·가평까지 넣고 중위값을 내면 "편의점 5곳 이상"처럼 서울에서는 아무것도
거르지 못하는 기준이 나온다 — 실제로 처음엔 그렇게 나왔다.

**백화점만은 개수로 셀 수 없었다.** 카카오에 백화점 카테고리 코드가 없어 키워드로
찾아야 하는데, `백화점` 반경 검색은 강남역 3km 안에서 879건을 돌려준다. 거리순 상위
15개가 전부 **백화점 안에 입점한 매장**이다("금강 롯데백화점노원점", 분류는
`패션 > 구두,신발`). 이름에 그 글자가 들어갈 뿐이라 개수도 못 믿고, 거리순으로
정렬해도 본체에 닿지 못한다.

그래서 수도권을 0.05° 격자 504칸으로 훑어 **분류가 실제로 백화점인 것**만 모았다
(75곳). 이후 거리는 그냥 계산이고 API 가 필요 없다. 조건도 개수가 아니라 거리로
건다 — 사용자가 궁금한 것도 "몇 개"가 아니라 "갈 만한가"다.

### ADR-21. 고르는 일의 끝은 나란히 놓고 보는 것 — 동네 비교 (2026-09-03)

카드를 하나씩 열었다 닫았다 하며 머리로 기억하게 두고 있었다. 그건 사람이 할 일이 아니다.
동네를 최대 셋까지 담아 통근·월세·오르막·편의점을 한 표로 보여주고, 줄마다 나은 값을 강조한다.

셋으로 제한한 건 넷부터는 화면에서 읽히지 않아서다. 그리고 **단지 비교는 다른 서비스도
하지만 동네 비교는 잘 없다** — 매물 단위로 보는 서비스에게 동네는 필터일 뿐 비교 대상이
아니기 때문이다. 우리는 동네를 정해주는 도구라 여기가 자연스러운 종착점이다.

### ADR-20. 지도에 없는 것을 데이터로 — 역과의 고도차 (2026-09-03)

**왜.** 자취에서 언덕은 월세 몇 만원보다 크게 체감된다. 짐 들고, 장 보고, 술 마시고
매일 걸어 올라가는 사람에게 "역에서 +40m"는 집을 고르는 기준이 된다. 그런데
**지도만 봐서는 절대 알 수 없다 — 평면에는 높이가 없다.**

호갱노노도 경사도를 보여주지만 아파트 단지 기준이다. 우리는 통근 도구니까 기준점이
**가장 가까운 역**인 게 맞다. 절대 고도(북한산이 높다)가 아니라 매일 오르내리는 차이가
실제 부담이다.

**데이터.** [opentopodata](https://www.opentopodata.org) 의 SRTM 30m. 무료·무인증에
한 번에 100지점이라 DEM 타일(49MB)을 받아 GeoTIFF 를 파싱하는 것보다 훨씬 싸다.

**함정 — SRTM 은 지표가 아니라 지표면 모델이다.** 레이더가 건물 옥상에서 반사되므로
도심에서 고도가 부풀려진다. 하필 우리가 관심 있는 곳이 가장 심했다:

| 지점 | 한 점만 읽었을 때 | 실제 |
|---|---|---|
| 종각역 | 93m | 30m 남짓 |
| 시청역 | 54m | 30m |
| 수서역 | 70m | 35m |

그 결과 **종로1가가 −54m**(역보다 54m 낮은 분지)로 나왔다. 종로는 평지다.

**해법.** 한 점이 아니라 **주변 3×3 을 100m 간격으로 읽어 최솟값을 지면으로 본다.**
건물은 국소 최대값이라 200m 범위 안에는 도로나 공터가 섞인다. 형태학적 열림(opening)으로
DSM 에서 DTM 을 근사하는 것과 같은 생각이다.

| | 평균 절대 오차 |
|---|---|
| 한 점 | 25.5m |
| 3×3 최솟값 | **5.8m** |

종로1가 −54m → **−1m**, 역삼동 −16m → **0m**, 화곡동·상도동 +9m(둘 다 실제로 언덕 동네).
표본이 9배가 되지만 216번 호출이라 하루 한도(1,000) 안에 든다.

**교훈.** 무료 전지구 고도 데이터는 **전부 지표면 모델**이다. 지표 고도가 필요하면
그 사실을 알고 보정하거나, 국토지리정보원 수치표고모델처럼 진짜 DTM 을 받아야 한다.
"고도 데이터를 받았다"와 "지면 높이를 안다"는 다른 말이다.

### ADR-19. 색 단계를 6개에서 4개로 줄이고, 해상도는 숫자로 준다 (2026-09-03)

**증상.** "지도를 보면 여기가 20분 걸리는지 30분 걸리는지 헷갈린다."

**측정.** 감이 아니라 팔레트 검증기로 색 거리를 쟀다. 인접 구간의 최악 쌍이
**ΔE 8.2**(정상 시야) 로 기준 15의 절반이었다. "완전한 색각으로도 구분이 어렵다"는
판정이고, 사용자가 느낀 것과 정확히 같다.

| 구성 | 인접 구간 ΔE | |
|---|---|---|
| 6단계 (기존) | 8.2 | ❌ |
| 5단계 | 10.4~12.0 | ❌ |
| **4단계** | **15.4** | ✅ |

**단일 색조로는 5~6단계를 그 간격으로 벌릴 수 없다.** 무지개로 바꾸면 벌어지지만
그건 안 된다 — 크기를 나타내는 색은 한 색조여야 한다. 색상이 바뀌면 사람은
"많다/적다"가 아니라 "다른 종류"로 읽는다.

**결정 세 가지.**

1. **단계를 4개로 줄인다.** 구분되지 않는 6단계보다 구분되는 4단계가 정보량이 많다.
2. **경계를 5분 배수로 맞춘다.** 예산을 균등 분할하면 40분에서 0·8·16·24·32 가
   나오는데 그런 숫자는 머리에 안 남는다. 0·10·20·30 은 보자마자 읽힌다.
   범례도 램프가 아니라 **실제 그려진 구간**을 보여준다.
3. **해상도는 색이 아니라 숫자로 준다.** 커서를 올린 곳의 통근 시간을 1분 단위로
   읽어준다. 격자를 이미 갖고 있어 조회가 산술 두 번이라([ADR-10](#adr-10-격자-렌더--등시선-2026-08-30))
   마우스를 움직이는 동안 계속 불려도 부담이 없다.

검증기는 옅은 두 단계가 배경 대비 3:1 미만이라 **"글자로 보정해야 한다"** 는 조건을
달았는데, 3번이 정확히 그 보정이다. 조건을 우회한 게 아니라 조건이 시킨 것을 했다.

**교훈.** "색이 헷갈린다"는 취향 문제로 보이지만 **측정 가능한 문제**였다.
눈으로 팔레트를 고르는 대신 거리를 재니 답이 바로 나왔고, 몇 단계까지 가능한지도
숫자로 나왔다.

### ADR-18. 건물은 확대했을 때만, 그것도 나중에 받는다 (2026-09-01)

동 시세가 "이 동네가 얼마"라면 건물은 "이 집이 얼마"다. 둘은 **다른 질문**이고, 묻는
시점도 다르다 — 동네를 고를 때와 그 동네를 들여다볼 때.

그래서 카카오 level 4(화면 폭 1~2km)를 경계로 갈아 끼운다. 그 배율에서는 동 하나가
통째로 화면이라 "이 동네 평균"이 더 이상 답이 아니다.

**데이터는 그때 받는다.** 62,243동 12MB 인데, 동네를 고르다 마는 사람에게 처음부터
물릴 이유가 없고 광역 배율에서는 그릴 수도 없다. 다만 보여줄 배율에 **도착해서야**
받기 시작하면 몇 초간 빈 지도를 보게 되므로, 두 단계 앞(level 6)에서 미리 시작한다.
확대는 대개 연속 동작이라 이 예측은 거의 맞는다.

**건물도 방 종류로 나눠야 했다.** 처음엔 건물당 값 하나였는데, 파크하비오는 원룸
월 98 / 투룸 월 187 / 쓰리룸 월 207 이다. 하나로 뭉치면 원룸을 찾는 사람에게 두 배
값을 보여준다. 동과 같은 면적 구간으로 나눠 담고, 고른 구간의 거래가 없는 건물은
아예 빼버린다 — 다른 구간 값을 대신 보여주면 "원룸 찾는데 왜 이 값이지"가 된다.

**단독·다가구는 건물 레이어에서 뺐다.** 지번이 없어 동 전체가 한 점으로 뭉쳐 있는데,
그걸 건물처럼 찍으면 동 레이어와 같은 정보를 두 번, 그것도 틀린 위치에 보여주는 셈이다.

### ADR-17. 조건을 URL 에 담는다 (2026-08-31)

[ADR-13](#adr-13-매물을-갖지-않는다--포지션을-앞단으로-2026-08-30) 에서 적었듯 이 도구는 리텐션이
구조적으로 안 나온다. 한 번 정하면 다시 올 이유가 없다.

그래서 **남에게 보내는 것**이 사실상 유일한 자연 유입 경로다. 커플이나 룸메이트는 어차피
"여기 어때?"를 주고받으며 고르므로, 그 대화에 링크가 끼어들 수 있으면 된다.

역 인덱스가 아니라 **역 이름**을 담는다. 인덱스는 그래프를 다시 만들면 바뀌어서 어제
보낸 링크가 오늘 엉뚱한 역을 가리킨다. `pushState` 가 아니라 `replaceState` 인 이유는,
슬라이더 한 칸마다 히스토리가 쌓이면 뒤로가기가 함정이 되기 때문이다.

### ADR-22. 없는 GTFS 를 기다리지 않고 만든다 (2026-09-07)

`6-3` 에서 "GTFS 를 안 받기로 했다"고 적었다. 그 판단은 **지하철만 할 때** 맞았다.
버스를 넣기로 하면서 뒤집혔고, 뒤집힌 이유를 남긴다.

**막힌 지점.** 국내 수도권 GTFS 는 KTDB 가 공개한 2023-03 판이 마지막이다. 3년 전
데이터로 "20분 안에 갈 수 있는 동네"를 그리면, 그 사이 생긴 노선과 없어진 노선이
그대로 틀린다. 이 도구는 **어디로 이사할지**를 정하는 데 쓰는 거라 그 오차가 결과를
바꾼다. 갱신되는 GTFS 가 필요한데, 그런 게 없다.

**대신 있는 것.** 원자료는 다 열려 있다. 노선 목록, 노선별 정류장 순서, 배차간격,
첫차·막차가 공공 API 로 나온다. GTFS 는 그걸 정해진 파일 여섯 개로 묶은 형식일 뿐이다.
그래서 **받는 대신 만든다**.

**왜 형식을 GTFS 로 맞추나.** 우리 파이프라인은 GTFS 를 먹지 않는다 —
`TimetableBuilder` 가 배차간격에서 시간표를 합성한다. 그런데도 GTFS 로 내보내는 이유:

1. **검증 도구가 생긴다.** 자체 포맷에는 "이게 맞는 파일인가"를 물어볼 데가 없다.
   GTFS 는 규격이 있어서 기계로 검사할 수 있다 → `--mode gtfscheck`
2. **엔진 교체 여지.** 나중에 OTP2 나 R5 를 붙일 일이 생기면 그대로 먹인다
3. 공개하면 실제로 쓰는 사람이 있다. 지금 대안이 3년 전 파일이라서

**frequency 기반으로 쓴다.** GTFS 는 두 가지 표현을 지원한다. 모든 편성의 시각을 다
적는 방식과, 대표 운행 하나 + 배차간격으로 적는 방식(`frequencies.txt`). 후자를 쓴다.
우리가 가진 게 배차간격이지 시각표가 아니고, 파일이 수십 배 작다. 그러면 만들어야 할
것은 "전 노선 모든 편성의 시각"이 아니라 **노선별 정류장 간 소요시간 한 벌**로 줄어든다.
ADR-23 이 그 한 벌을 어떻게 채웠는지다.

결과: 정류장 53,383 · 노선 2,971 · 운행 5,649 · 4.3MB · 규격 오류 0.

### ADR-23. 버스 속도는 노선 유형이 아니라 정류장 간격에서 온다 (2026-09-07)

`stop_times.txt` 를 채우려면 정류장에서 정류장까지 몇 초인지가 있어야 한다.
그게 이 작업에서 제일 어려웠고, 세 번 갈아엎었다.

**1차 — 유형별 표정속도표.** 간선 19km/h, 지선 16, 마을 14 … 로 시작했다.
검증기가 이걸 잡았다:

```
노선 총 소요시간(분)  중앙 66 · 상위10% 131 · 최대 480
```

편도 **8시간**짜리 운행. 8829번(이천터미널→인천공항)이었다. 데이터를 열어보니
정류장 87개 중 39개 구간이 3km 를 넘는다 — 고속도로 IC 사이 구간이다. 거기에
경기버스 표정속도 22km/h 를 먹인 결과였다. **데이터가 아니라 모델이 틀렸다.**

**2차 — 실측을 쓴다.** 서울 API 의 `getStaionByRoute` 는 노선 하나를 부르면 그 순간
전 구간의 속도(`sectSpd`)를 준다. 차량을 1분마다 추적해 정류장 통과를 관찰하는 방식보다
요청이 300배 적다. 대신 그 값은 **그 순간**이라 30초 만에 104구간 중 12개가 바뀐다.
그래서 시간대별로 여러 번 찍어 중앙값을 쓴다(ADR-25 의 스케줄).

문제는 **`sectSpd` 가 서울 자체노선 814개에만 있다.** 경기 2,157개에는 없고,
앞으로도 안 생긴다. 실측만으로는 구간의 17% 밖에 못 채운다.

**3차 — 실측에서 곡선을 배워 나머지에 적용한다.** "고속도로 구간인가"를 알려면
도로망이 필요하다. 도로망 없이 쓸 수 있는 대리 지표가 **정류장 간격**이다.
정류장을 3km 마다 세우는 구간은 정의상 고속 구간이고, 200m 마다 세우는 구간은 아니다.
서울 실측 33,535구간이 그 관계를 그대로 보여줬다:

| 정류장 간격 | 중앙 속도 | 관측 |
|---|---|---|
| 0~200m | 15 km/h | 4,267 |
| 200~400m | 21 | 14,296 |
| 400~700m | 30 | 10,488 |
| 700~1,200m | 33 | 3,284 |
| 1,200~2,000m | 37 | 636 |
| 2,000~3,500m | 47 | 311 |
| 6,000~10,000m | 63 | 30 |

그래서 표를 지우고 **이 곡선을 실측에서 학습한다**(`Gtfs.SpeedModel`).
스냅샷이 쌓일수록 곡선이 정확해지고, 그게 수집 스케줄을 계속 돌리는 이유다.

규제 둘을 걸었다. 유형별로 쓰려면 칸마다 관측 100개 이상, 아니면 거리만 본다.
그리고 **거리가 늘수록 느려지지는 않는다**고 본다 — 3.5~6km 칸이 아래 칸보다
느리게 나오는데 관측이 102개뿐이라 잡음으로 판단하고 누적 최대로 눌렀다.

결과: 최대 소요시간 480분 → **235분**, 시속 90km 넘는 구간 7개 → **0개**.

**곁다리로 잡은 것.** 799번의 한 구간이 직선 5.6km 를 26초에 갔다 — 시속 777km.
API 가 준 도로거리가 직선거리보다 짧았다. 도로가 직선보다 짧을 수는 없으니
그럴 땐 값을 버리고 직선거리를 쓴다. 값 하나가 틀린 건데 그게 검증기까지 살아남았다.

### ADR-24. 중복 노선은 버리는 게 아니라 합친다 (2026-09-07)

서울 API 는 서울을 지나는 **경기·인천 노선도 함께** 준다. 1,363개 중 635개가 그것이다.
그냥 두면 같은 버스가 두 대로 세어져 배차가 두 배가 되고, 도달권이 실제보다 넓어진다.

**첫 시도 — 노선번호로 짝짓기.** 597개 중 **4개**만 맞았다. 서울은 외부 노선에
도시명을 붙여 준다: `1-1김포`, `1002화성`, `M6439인천`.

**두 번째 — 좌표로 짝짓기.** 정류장을 130m 격자에 스냅해 겹침을 보니 557개가 붙었다.
그런데 `3000인천` ↔ `3000-1` 처럼 **다른 노선끼리 붙은 것**이 섞였다.

**세 번째 — id 를 봤다.**

```
서울  208000024  ↔  경기  GGB208000024
```

**서울 id 앞에 `GGB` 를 붙이면 경기 id 다.** 597개 중 549개가 이 규칙으로 붙고,
인천 38개는 하나도 안 붙는다(우리한테 인천 데이터가 없으니 맞는 결과다).
좌표 대조로도 같은 노선 전체를 가리킨다 — 정류장 수 비 1.00, 겹침 93~100%.

여기서 판단이 갈렸다. 중복이면 하나를 버리면 되는데, **어느 쪽을 버리나.**
둘을 비교해보니 서로 없는 걸 갖고 있었다:

| | 서울판 | 경기판 |
|---|---|---|
| 방향(상·하행) | 498개 노선 ✅ | 전부 null ❌ |
| 구간 거리 | 549개 전부 ✅ | 없음 ❌ |
| 요일별 배차 | 한 값뿐 ❌ | 평일·토·일 ✅ |

그래서 **버리지 않고 합쳤다** — 노선 정보는 경기 것, 정류장 기하는 서울 것.
549개 노선이 방향과 실제 도로거리를 얻었다.

**남은 경기 1,407개는 방향이 없다.** `updowncd` 가 전부 null 이라 상·하행이 한 줄로
이어져 온다. 300번은 정류장 163개인데 82번째가 기점에서 가장 멀고(30.9km) 마지막은
기점과 0.0km 다 — 왕복이 한 줄에 들어 있다. 안 자르면 "기점→종점 60분"이
"기점→종점→기점 120분"이 돼 도달권이 절반으로 줄어든다. 기점에서 가장 먼 지점을
반환점으로 보고 자르되, 그 지점이 열의 끝(80% 이후)이나 앞(10% 이전)에 있거나
종점이 기점으로 안 돌아오면 편도로 둔다.

**그리고 정류장 id 도 두 벌이다.** 같은 기둥이 `S105000123` 과 `G228001456` 로 따로
들어 있다. 이걸 안 이어주면 경기 버스에서 내려 서울 버스로 갈아타는 경로가 아예 안
나온다. 60m 안의 서울↔경기 쌍 9,186개를 `transfers.txt` 로 이었다. 같은 기관 안의
길 건너편 정류장은 넣지 않았다 — 라우터가 자체 도보 그래프로 잇고, 넣으면 파일만 커진다.

### ADR-25. 수집은 사람이 안 보는 동안 돈다 (2026-09-07)

`sectSpd` 는 **그 순간의 값**이라 한 번 찍어선 쓸모가 없다. 아침 8시와 밤 10시가
다르고, 같은 시각에도 30초 만에 바뀐다. 시간대별로 며칠 찍어 중앙값을 내야 한다.
그런데 API 일일 한도가 있어서 하루에 다 못 받는다 — 실제로 첫날 1,363개 중 623개에서
막혔다. 즉 **여러 날에 걸쳐 나눠 받는 수밖에 없다.**

Windows 작업 스케줄러에 걸었다(`tools/collect.ps1`, 하루 5회: 08:00, 12:00, 15:00,
18:30, 22:00). 사람이 안 보는 동안 도는 것이라 설계에서 지킨 게 넷 있다:

1. **모든 단계가 재개 가능하다.** 이 프로젝트에서 같은 실수를 네 번 했다 — 실거래가
   45분 날림, 정류장 페이징 truncation, 도시코드 오류, Overpass 타일. 무인 실행은
   실패를 아무도 안 보므로 이게 더 중요하다
2. **한 단계가 실패해도 나머지는 돈다.** 일일 한도는 종류별로 따로 걸린다
3. **실행 사본으로 돈다.** 개발 중에 jar 를 다시 빌드하면 도는 JVM 이
   `ClassNotFoundException` 으로 죽는다(실제로 겪었다). 시작할 때 복사해 격리한다
4. **매번 결과물까지 다시 만든다.** 수집만 하고 쌓아두면 "언제 반영되나"를 사람이
   챙겨야 한다. 수집 → GTFS 생성 → 검사까지가 한 번의 실행이다

**그리고 좋아지고 있는지를 파일 하나로 본다** (`data/logs/progress.csv`):

```
time,snapshots,measured_segments,measured_pct,stops,routes,trips,zip_kb,speed_curve
2026-09-07 22:47,1,32970,17.3,53383,2971,5649,4358,"0m:15 200m:21 400m:30 …"
```

여기서 **실측 비율은 17% 근처에서 멈춘다.** `sectSpd` 가 서울 자체노선에만 있어서다.
그러니 그 숫자를 목표로 삼으면 안 된다. 스냅샷이 쌓이면서 실제로 좋아지는 건
맨 오른쪽 **속도 곡선**이고, 그 값이 흔들리다 멎으면 표본이 충분해진 것이다.
그때가 수집 빈도를 줄여도 되는 시점이다.

**검사를 직접 썼다.** MobilityData 의 공식 validator 가 있고 그게 더 꼼꼼하다.
그런데도 `--mode gtfscheck` 을 만든 이유는 **이게 무인으로 돌기 때문**이다. 하루 5번
GTFS 를 다시 만드는데 그때마다 사람이 jar 를 내려받아 돌릴 수는 없다.
검사는 두 층이다:

* **규격** — 참조 무결성, 필수 필드, 정렬. 틀리면 라우터가 아예 못 읽는다
* **말이 되는가** — 구간의 함축 속도, 노선 총 소요시간. 규격은 맞는데 버스가 시속
  200km 로 달리는 파일은 공식 validator 도 통과시킨다. 그건 우리가 봐야 한다

두 번째 층이 실제로 잡은 것이 ADR-23 의 480분과 777km/h 다. 규격 검사만 있었으면
둘 다 통과했을 것이다.

### ADR-26. 만든 GTFS 를 카카오맵으로 대조했다 (2026-09-07)

`gtfscheck` 는 "규격에 맞나 / 말이 되나"까지만 본다. 시속 200km 짜리 구간은 잡지만
**전체가 일정하게 빠른 것**은 못 잡는다. 그건 바깥 기준값과 대봐야 안다.
그리고 실제로 그랬다 — 처음 만든 GTFS 는 **30% 빨랐고 규격 검사를 멀쩡히 통과했다.**

#### 어떻게 대는가

카카오맵 대중교통 길찾기는 경로를 leg 단위로 쪼개서 준다:

```
4312번 · 강남역10번출구 승차 · 구룡산입구 하차 · 정류장 10개 · 1607초 · 5565m
```

우리 `stop_times.txt` 가 담은 것과 **정확히 같은 단위**다. 노선번호 + 승하차 정류장 +
정류장 수로 맞추면 바로 대조된다. 길찾기 한 번에 leg 이 10~16개 나오니 OD 46개로
표본 1,158구간이 됐다. 전수 대조는 어느 서비스든 약관 위반이라 하지 않는데,
이 방식이면 소량 조회로도 표본이 충분하다.

#### 브라우저를 어떻게 몰았나 — 세 번 갈아엎었다

1. **입력창에 타이핑** → 자동완성이 끼어들고 패널이 다시 그려지면서 도착지가 지워진다
2. **좌표 클릭** → 창 크기가 바뀌면 어긋난다
3. **URL + 선택자** — `map.kakao.com/link/from/이름,위도,경도/to/…` 로 좌표를 넣고
   `document.querySelector('a.transit').click()` 로 대중교통 탭을 누른다. 안 흔들린다

응답이 한 건 190KB 라 그대로 읽으면 문맥이 감당이 안 된다. 그래서 페이지의
`XMLHttpRequest` 를 가로채 응답을 잡아두고 **브라우저 안에서 요약**한 뒤 꺼냈다.
(직접 `fetch` 를 부르는 건 막혀 있다 — 페이지가 스스로 부르게 해야 한다.)

이 레시피가 정해지고 나서 **에이전트 여섯을 각자 탭 하나씩 붙여 병렬로** 돌렸다.
OD 34개가 4분 40초에 끝났다.

#### 처음 대본 결과

| | 카카오 | 우리 | |
|---|---|---|---|
| 표정속도 | 13.6 km/h | 22.8 km/h | **1.67배 빠름** |
| 편향 | | −263초 (−29.8%) | ±3분 이내 45% |
| 구간거리 ÷ 직선거리 | 1.07 | **1.01 로 쓰고 있었음** | |

#### 왜 틀렸나 — 그리고 무엇을 고칠 수 있었나

**구간거리 1.01 은 잰 방법이 틀렸다.** 그 값은 서울 구간 하나짜리 비의 중앙값이라
짧은 구간이 표를 지배했다. 사람이 실제로 타는 단위(여러 구간을 이어 붙인 것)로 재면
**1.066** 이다. 이건 직접 재는 값이라 그냥 고쳤다.

**속도와 정차는 구분되지 않았다.** 우리가 30% 빠른 이유로 두 설명이 가능했다 —
주행이 빠르거나, 정류장당 시간이 짧거나. 그런데 **자료로는 둘을 못 가른다.**
MAE 지형이 대각선 골짜기다:

```
        정류장당 20초  40초  58초  80초  100초
주행×0.8      350    229   155   153   229
주행×1.0      273    177  [146]  199   301
주행×1.2      214    157   170   261   384
주행×1.4      179    166   219   339   470
```

그래서 **잰 값(sectSpd)은 건드리지 않고 재본 적 없는 항에 보정을 넣었다.**
정류장 통과 비용은 감속·정차·가속·신호를 담는데 20초로 잡혀 있었다.

#### 반대쪽 — 광역버스는 오히려 느렸다

도심 OD 34개로 맞추고 나니 광역 회랑 12개에서 반대 방향 오차가 드러났다:
**광역급행 편향 +660초.** 일괄 정차 비용이 고속 구간을 과대 처벌한 것이다.

여기서 앞의 식별 문제가 풀린다. **정류장 간격이 1.5km 를 넘으면 정류장이 몇 개
없어서 거리 항이 지배하고, 그 영역에서는 속도가 식별된다.** 그래서:

* 짧은 구간 → 정류장 통과 비용 하나로 맞춘다
* 긴 구간 → 속도 배율 하나로 맞춘다

긴 구간에서 곡선이 틀렸던 이유도 분명하다. 속도 곡선은 서울 시내버스 `sectSpd` 로
배웠는데 **6~10km 간격 칸의 관측이 30개뿐**이다. 서울 시내에 그런 구간이 거의 없다.
경기 광역버스가 정확히 그 영역이다.

**그리고 맞추기는 스스로 멈추지 않는다.** 배율을 자유롭게 두니 5km 넘는 구간이
중앙 103km/h 로 나왔다. 고속도로 버스 제한속도가 100km/h 다. 보정계수가 "곡선이
얼마나 낮았나"를 흡수하다가 불가능한 값까지 민 것이다. 95km/h 뚜껑을 씌웠다.

#### 최종

| | 처음 | 지금 |
|---|---|---|
| 표정속도 (카카오 13.9 대비) | 22.8 (1.67배) | **15.0 (1.08배)** |
| 편향 | −263초 (−29.8%) | **+2초 (−1.4%)** |
| MAE | 292초 | **141초** |
| ±3분 이내 | 45% | **74%** |
| 광역급행 편향 | +660초 | **−57초** |

보정값: 정류장 통과 **62초** · 구간거리 **×1.066** · 1.5km↑ 속도 **×1.10** (상한 95km/h).
**OD 를 반으로 갈라 한쪽으로 맞추고 다른 쪽으로 평가했다** — 같은 자료로 맞추고
같은 자료로 자랑하면 검증한 게 아니다. 평가셋 편향 −20초 · MAE 147초 · ±3분 73%.

#### 대조기 자신이 틀린 경우가 더 많았다

매칭 실패 189건 중 **87건이 우리 대조기 버그**였다 — 카카오 `홍대입구역(중)` 과
우리 `홍대입구역(중앙)` 을 다른 정류장으로 봤다. 괄호 안까지 지우니 붙었다.
17번 노선이 카카오 400초 vs 우리 4110초로 나온 것도 데이터가 아니라 대조기였다 —
승차 정류장이 순환 노선에 두 번 나오는데 첫 번째만 보고 "한 바퀴 돌아가는" 조합을
골랐다. **데이터 결함으로 셀 뻔했다.** 바깥 기준값과 대는 일은 대조기부터 의심해야 한다.

### ADR-31. R5 로 넘긴다던 계획이 깨졌다 — RAPTOR 를 직접 (2026-09-08)

[ADR-3](#adr-3-raptor-대신-시간-의존-dijkstra) 은 이렇게 적어뒀다:

> **언제 뒤집나.** 버스가 들어와 정류장이 5만 개가 되는 시점. 그때는 직접 짜지 말고
> R5 로 넘긴다.

그 시점이 왔다. 그리고 **[ADR-22](#adr-22-없는-gtfs-를-기다리지-않고-만든다-2026-09-07)
에서 GTFS 를 만든 이유 중 하나가 정확히 이것**이었다 — "나중에 엔진을 바꿀 여지".
R5 는 GTFS + OSM 을 먹는데 우리한테 둘 다 있다. 계획대로면 붙이기만 하면 됐다.

**붙여보니 안 됐다.**

| | 확인한 것 |
|---|---|
| **R5** | Maven 배포가 **2017-05 에 멈춰 있다.** `maven.conveyal.com` 의 최신이 `2.0.0-pre` 인데 지금 R5 는 7.x 다. 라이브러리로 내놓는 물건이 아니게 됐고, Conveyal Analysis 의 일부로 돌린다 |
| **OTP2** | Maven Central 에 본체(`org.opentripplanner:otp:2.5.0`)는 있는데 전이 의존성 `onebusaway-gtfs` 가 없어서 해결이 깨진다. 별도 저장소를 물려야 한다 |

그리고 OTP 는 애초에 **서버**다. 출발지 621개 × 슬롯 20개를 도는 배치에 임베드할
물건이 아니고, 미니PC 16GB 제약도 있다([mini PC batch infra](#6-열린-항목)).

**추측이 아니라 실제로 `gradle` 로 붙여보고 얻은 결과다.** 계획이 3년 묵으면 이렇게
된다 — 그 계획을 적을 때 R5 는 라이브러리였다.

#### 그래서 직접 짰다

`Raptor.kt` 는 300줄이 안 된다. 우리 자료구조가 이미 RAPTOR 모양이라 그렇다 —
[ADR-6](#adr-6-합성-시간표를-쓰되-탐색은-진짜-시간표만-안다) 에서 시간표를 평탄 배열로
편 것이 그대로 쓰인다.

**frequency 를 펴지 않는다.** 배차 10분짜리를 18시간치 편성으로 펴면 운행 11,218개가
120만 개, 정차가 4천만 행이 된다. 대신 "그 시각 이후 첫 차"를
`start + k×headway` 로 O(1) 에 푼다. 우리 합성 시간표가 원래 하던 계산과 같아서
새로 검증할 것이 없다.

붙이면서 두 가지를 고쳐야 했다.

**1. 피드끼리 남남이었다.** 지하철·버스 GTFS 는 id 공간이 달라 서로 환승이 없다.
강남역에서 90분 안에 닿는 정류장이 51,583개 중 **679개**뿐이었다 — 지하철만 타고
다닌 것이다. 400m 안의 정류장끼리 도보 환승을 만들어 붙였다 → 34,708개.

**2. 환승이 공짜였다.** GTFS `frequencies` 는 창 시작시각부터 배차마다 출발한다.
그런데 우리 지하철 창은 전 노선이 05:30·07:00… 로 똑같이 시작하고 버스 첫차도
05:00 에 몰려 있다. 전 노선이 같은 순간에 출발하니 갈아탈 때 기다림이 0 이 됐다.
노선마다 결정론적 위상을 줘서 어긋나게 했다.

> ADR-6 의 위상 정렬과 목적이 반대다. 거기선 **타고 지나가는** 승객의 대기를 0 으로
> 만드는 게 목적이었는데, RAPTOR 는 같은 패턴에 머무르면 애초에 다시 안 타므로
> 그건 저절로 된다. 여기서 필요한 건 **새로 타는** 승객이 제대로 기다리게 하는 것이다.

**입력은 여전히 GTFS 다.** 엔진을 바꿀 여지는 그대로 남는다 — R5 가 다시 라이브러리로
나오거나, 갱신된 공개 GTFS 가 생기면 그때 갈아끼우면 된다. GTFS 를 만든 값은 여기서 한다.

### ADR-32. 도착 축을 역 621개에서 동네 1,768개로 (2026-09-08)

지금까지 행렬은 `출발역 → 도착역 621개` 였다. 지하철만 있을 땐 맞았다 — 화면은
역 주변을 원으로 부풀려 등시선을 그렸고, 역이 곧 도달 지점이었다.

버스가 들어오면 그게 깨진다.

* 정류장이 6만 개라 도착 축에 다 넣을 수 없다 (6만 × 슬롯 × 출발지면 수 GB)
* **"가까운 역"이라는 개념이 의미를 잃는다** — 역에서 먼 동네도 버스로는 가깝다

그래서 **화면이 이미 쓰고 있는 단위**로 바꿨다. 이 앱의 주인공은
[ADR-14](#adr-14-지도의-주인공을-점에서-동네-시세로-2026-08-31) 이후 법정동 1,768개다.
도착 축을 거기로 맞추면 부풀리기 없이 바로 읽는 값이 되고, 파일도 작아진다.

#### 슬롯을 232개에서 20개로

10분 간격 232슬롯은 지하철만 계산할 때(전체 2.3초) 공짜였다. 탐색 한 번이 80ms 가
되면 621 × 232 = **4시간**에 파일이 **254MB** 다. 이사 갈 동네를 고르는 데 10분
해상도는 필요 없다.

| | 전 | 후 |
|---|---|---|
| 슬롯 | 232개 (10분 간격, 05:30~) | **20개** (출근 도착 07~10시, 퇴근 출발 17~23시, 30분 간격) |
| 도착 축 | 역 621 | **동네 1,768** |
| 전체 생성 | 2.3초 (지하철만) | **4~6분** (지하철+버스+도보) |
| 파일 | 89MB | **20MB** (출발지당 34KB) |

#### 출발지는 그대로 역이다

매니페스트의 `stations` 키를 그대로 두고 `dongs` 를 더했다. 그래서 출발지
콤보박스·마커·공유 링크가 손댈 필요 없이 돈다. 바뀐 건 도착 축뿐이다.

**웹은 파일 세 개만 고쳤다** — `provider.ts`(행렬 열), `types.ts`(이름),
`grid.ts`(좌표만 받게), `main.ts`(필드를 동네에서 칠하게).
[ADR-9](#adr-9-프론트는-reachabilityprovider-만-본다) 가 노린 게 이거였고,
실제로 지도·필터·카드는 한 줄도 안 건드렸다.

**축을 바꾸면서 놓친 자리 하나.** `coreBounds` 가 `within`(이제 동네 색인, 최대 1767)을
`meta.stations`(621개)에서 찾고 있었다. 색인이 621을 넘으면 `undefined` 가 나와
지도가 통째로 죽는다. 축을 바꿀 때 같이 안 바꾼 곳은 타입이 안 잡아준다 —
둘 다 `number` 색인이라서다.

### ADR-30. 지하철 승차시간을 처음으로 직접 쟀다 (2026-09-08)

지하철 도달권은 카카오맵 18쌍 대조로 편향 −0.9분까지 맞춰놨다고 적어뒀다.
[ADR-29](#adr-29-결론을-반박시켰더니-25건-중-24건이-뒤집혔다-2026-09-08) 의 반박
검증이 그 논거를 무너뜨렸다 — **그건 문앞-문앞 값이라 대기와 주행의 오차가 상쇄돼
감춰진다.** 즉 승차 구간 시간 자체는 검증된 적이 없었다.

버스에 쓴 대조 방식을 그대로 지하철에 돌렸다. OD 40개 → 지하철 leg 397개 →
우리 GTFS 와 붙은 구간 215개.

#### 드러난 것 셋

**1. 승차시간이 8.8% 짧다.** 편향 −95초, 노선별로 −5%~−17%. 원인은 단순했다 —
`Headways.segmentSeconds` 의 표정속도는 **구간을 달리는 속도**지 감속·정차·가속을
담지 않는다. 역당 10초를 붙였다(OD 절반으로 맞추고 나머지로 평가).

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 승차 구간 편향 | −95초 (−8.8%) | **−4초 (−1.2%)** |
| MAE | 130초 | **81초** |
| ±3분 이내 | 78% | **90%** |
| 문앞-문앞 편향 | −0.9분 | **−0.4분** |

**문앞-문앞이 안 나빠진 게 중요하다.** 반박 검증은 "대기 +3.3분 / 주행 −12.2% 가
상쇄 중"이라고 봤는데, 실측 주행 편향은 −8.8% 였고 그걸 고쳐도 총합이 오히려
좋아졌다. **상쇄는 있었지만 그 크기는 아니었다** — 반박이 옳게 의심했고, 실측이
그 크기를 정정했다.

**2. 순환선이 선형으로 잘려 있었다.** `lineSequences()` 가 노선을 선형 체인으로
잇는데 순환선은 그렇게 표현이 안 된다. 2호선 체인은
`까치산…도림천 [신도림 …한 바퀴… 신도림]` 이라 절단점을 가로지르는 통행이 반대로
한 바퀴 돌았다.

| | 고치기 전 | 고친 뒤 | 실제 |
|---|---|---|---|
| 강남→홍대입구 | 26정거장 | **17정거장** | 16 |
| 교대→합정 | 28 | **15** | 14 |
| 시청→신도림 | 33 | **10** | 10 |

같은 노드가 8칸 이상 떨어져 두 번 나오면 그 사이가 한 바퀴다. 그 구간만 떼어
**두 바퀴**짜리 운행을 따로 내보낸다. 지선이 붙은 원래 체인도 그대로 둔다.

**3. 원본 GML 의 역명이 하나 뒤섞여 있었다.**

```
문화공원동대문역사  →  동대문역사문화공원
```

이것만으로 9개 구간이 "역이 없다"로 떨어지고 있었다. 글자 구성이 같은 짝을 전수로
훑어 이 하나만 나왔다. GML 은 남의 파일이라 읽을 때 바로잡는다.

#### 그리고 2020년 부채의 크기가 처음 숫자로 나왔다

남은 미매칭 26건은 대부분 우리 망에 아예 없는 노선이다:

| 빠진 것 | 이 표본에서 |
|---|---|
| GTX-A (킨텍스·운정중앙·동탄) | 13구간 |
| 5호선 하남 연장 (하남검단산) | 8구간 |
| 신분당선 신사 연장 | 6구간 |
| 8호선 별내 연장 (동구릉) | 1구간 |

**교훈.** 집계 지표 하나로 검증했다고 하면 안 된다. −0.9분은 맞는 숫자였지만
그 안에서 두 항이 반대로 틀려 있었고, 그건 **항을 쪼개 재봐야** 보였다.

### ADR-29. 결론을 반박시켰더니 25건 중 24건이 뒤집혔다 (2026-09-08)

카카오 대조로 남은 미매칭 174건과 이상치의 원인을, 에이전트 넷에게 **서로 다른
각도로** 파게 했다(노선누락 · 구간누락 · 이상치 · 체계편향). 그리고 각 결론마다
**다른 에이전트에게 반박을 시켰다** — "직접 세어서 확인하고, 애매하면 반박 쪽으로
기울여라". 에이전트 29개, 결론 25건, 살아남은 것 **1건**.

반박률 96%는 진단이 엉터리였다는 뜻이 아니다. 대부분은 "원인은 맞는데 분류가
반대이거나 건수가 틀렸다"였고, **그 정정이 실제 수정 방향을 바꿨다.**

#### 뒤집힌 것 중 실제로 코드를 바꾼 셋

**1. 속도 필터가 고속 구간을 통째로 버리고 있었다.**
`MAX_KMH = 80` 은 GPS 잡음을 자르려던 값인데, 원자료를 세어보니:

```
3,500~6,000m   287개 중 185개(64.5%) 버림 · 중앙 95 → 31 km/h
6,000~10,000m  204개 중 173개(84.8%) 버림 · 중앙 86 → 63 km/h
```

속도 곡선의 긴 쪽이 **남은 느린 꼬리**로만 만들어졌다. 내가 "3.5~6km 칸이 아래
칸보다 느린 건 표본이 적어 생긴 잡음"이라 보고 단조화로 눌렀던 그 골짜기가
**이 필터가 만든 것**이었다. 자기가 만든 왜곡을 잡음으로 오해했다.
길이별로 자르게 바꿨다(500m 미만 60 · 1.5km 미만 80 · 그 이상 110km/h).

곁들여 보정계수 탐색 범위도 1.0~3.0 이었다 — "곡선이 낮다"는 가정을 코드에 박아둔
것이었다. 필터를 고치자 긴 구간이 오히려 빨라져 계수가 아래로 가야 했는데 갈 수가
없었다. 0.40~3.00 으로 넓히니 ×0.85 로 수렴한다.

**2. 편도 순환을 왕복으로 오인해 잘랐다.**
처음 진단은 "대조기 버그"였는데 반박이 원자료를 다시 세어 **빌더 결함**으로
뒤집었다. 안산 80A·N80A·60B·N60B 는 원자료에 승하차가 멀쩡히 이어져 있는데
절단선이 그 사이에 떨어져 사라졌다. 되짚음 판정(좌표 150m, 45%)을 넣어
순환 199개를 온전히 남긴다.

**3. (미정차)·(가상) 형상점** — [ADR-28](#adr-28-버스가-서지-않는-지점을-정류장으로-세고-있었다-2026-09-07) 로 별도 기록.

#### 반박이 내 논거 하나를 무너뜨렸다

나는 "같은 카카오인데 지하철은 −0.9분까지 맞았으니 출처 탓이 아니다"를 근거로 쓰려
했다. 반박은 그 대조가 **문앞-문앞 집계**라 상반된 두 오차(대기항 +3.3분 /
주행속도 −12.2%)를 상쇄해 감춘다고 지적했다. 결론(출처 탓이 아니다)은 유지되지만
그 논거로는 못 쓴다. 쓰기 전에 걸러졌다.

#### 살아남은 1건

서울 맞춤버스는 출퇴근 방향이 별개 노선으로 등록돼 번호가 `8773출근`/`8773퇴근`
인데 카카오는 `8773` 로 준다(대조기 문제, 3건). 반박도 이건 재현했고, 다만 근거의
숫자 하나(397초 → 413초)와 "8xxx 가 목록에 다 있다"는 과잉 일반화를 정정했다.

#### 아직 안 고친 것 — 근거와 함께

| 무엇 | 규모 | 어디 |
|---|---|---|
| 노선번호에 한글 접미(`1300인천`, `110A고려대`) | 서울 1,363개 중 607개(44.5%) | `Gtfs.kt` route_short_name — **공개 GTFS 품질 문제이기도 하다** |
| 방향 경계를 넘는 승차가 사라짐 | 관측 23건 (서울 13 + 경기 10) | `loadSeoulStops` 의 `groupBy { dir }` |
| 경기 detour 가 서울과 다르다 | 서울 1.065 · 경기 1.101 | 전역값 하나를 쓰고 있다 |
| 경기 마을버스 0개 | 유형 분포에 아예 없다 | TAGO 가 안 준다. GBIS 필요 |
| `8342`·`8343`·`8839`·`8862` | 4개 | 두 원자료 어디에도 없음. 실체 미확인 |
| `sectSpd` 의 정의 | — | 순간 주행속도인지 구간 평균인지 문서가 없다. 정차를 얼마나 품는지 판정 불가 |

### ADR-28. 버스가 서지 않는 지점을 정류장으로 세고 있었다 (2026-09-07)

**보정으로 덮은 것을 원인으로 착각할 뻔했다.** 이 항목은 그 기록이다.

카카오 대조에서 광역급행 편향 +660초가 나왔을 때, 나는 "긴 구간에서 속도 곡선이
낮다"고 보고 속도 배율을 도입해 맞췄다. 배율이 1.80 까지 올라갔고 5km 넘는 구간이
중앙 103km/h 가 됐다 — **고속도로 버스 제한속도를 넘었다.** 95km/h 뚜껑을 씌워
가렸는데, 뚜껑이 필요하다는 것 자체가 신호였다.

진단 에이전트가 원자료를 세어 진짜 원인을 찾았다. 경유 목록에는 정류장이 아닌 것이
섞여 있다:

```
양재IC(미정차) · 서울TG(미정차) · 금토JC(미정차) · GS주유소(가상)
```

노선 모양을 그리려고 넣은 **형상점**이다. 경기 경유 148,352개 중 11,409개(7.7%),
서울 88,885개 중 10,400개(11.7%). 이걸 정류장으로 넣고 정차시간을 물리면 산출물에
가짜 정차 **30,173행**이 생기고, 정류장당 62초면 511시간이 없는 시간이 된다.

**그리고 이런 지점은 고속도로 구간에만 몰려 있다.** 그래서 광역·직행좌석만 골라
느리게 만들었다. 도심 노선은 멀쩡했으니 전체 통계로는 안 보였다.

거리는 살리고 정차만 뺐다 — 버스는 그 지점을 지나가긴 한다.

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 긴 구간 속도 배율 | ×1.80 (억지로 맞춘 값) | **×1.10** |
| 시속 100km 넘는 구간 | 1,245개 | **0개** |
| 광역급행 편향 | +660초 | **−57초** |
| 전체 편향 | −20초 | **+2초 (−1.4%)** |
| 정류장 / 정차 | 53,383 / 430,572 | 50,842 / 400,399 |

배율이 **스스로 1.80 → 1.10 으로 내려온 것**이 원인을 제대로 잡았다는 확인이다.

**교훈.** 맞추기(fit)는 원인을 묻지 않는다. 계수가 물리적으로 이상한 값으로 가면
그건 모델이 무언가를 흡수하고 있다는 뜻이고, 뚜껑을 씌울 게 아니라 그 무언가를
찾아야 한다. 대조 숫자만 보고 있었으면 못 찾았다 — 원자료를 세어야 보였다.

### ADR-27. 보정을 상수에서 빼내 스스로 다시 맞추게 (2026-09-07)

정류장 통과 61초는 **밤(22:19) 속도 표본 위에서** 맞춘 값이다. 스케줄이 낮 스냅샷을
찍기 시작하면 순항 속도가 느려지고, 그러면 이 값도 내려가야 한다. 상수로 두면 사람이
코드를 고쳐야 하고, **그러면 안 고쳐진다.**

```
tools/reference-bus.json      카카오맵에서 받아 고정해둔 구간 564개
gtfs_match.py --fit           대조 → 보정값 재계산 → data/calibration.json
Gtfs.kt loadCalibration()     생성할 때 그 파일을 읽는다 (없으면 기본값)
collect.ps1                   생성 → 검사 → 대조·보정 → (바뀌었으면) 재생성
```

값이 1~2초씩 진동해 매번 재생성이 돌기에 불감대(4초 / 0.01 / 0.05)를 뒀다.
다섯 번 돌려 수렴을 확인했다.

`progress.csv` 에 회차마다 `dwell_sec, detour, kakao_bias_sec, kakao_mae_sec,
kakao_within3min` 이 남는다. **낮 표본이 쌓이면 정류장 통과 비용이 내려가야 한다 —
안 내려가면 다른 데가 틀린 것이다.** 그 관찰이 이 표의 목적이다.

## 5. 검증

두 가지를 각각 카카오맵과 대조한다. 전수 대조는 어느 서비스든 약관 위반이라
표본만 본다 — 대신 표본 하나에서 여러 구간이 나오는 방식을 골랐다.

### 5-1. 지하철 (2026-08-21)

카카오맵 지하철 경로와 표본 18쌍 대조 (강남 출발, 평일 20:30).

```bash
./gradlew :builder:run --args="--mode compare --gml data/raw/metro_graph.gml \
  --reference tools/reference-kakao.json"
```

| 지표 | 수정 전 | 수정 후 |
|---|---|---|
| 평균 편향 | +3.4분 | **−0.9분** |
| 절대 평균 오차 | 4.3분 | 3.8분 |
| ±7분 이내 | 83% | **89%** |

**비교 정의를 먼저 맞춰야 한다.** 카카오의 대표 숫자는 승차~하차만 세고 우리 값은
대기를 포함한다. 기준값을 `(승차시각 − 기준시각) + 승차시간` 으로 환산하지 않으면
우리가 항상 나쁘게 나온다.

**검증이 잡아낸 것.** 20~23시 배차 추정이 7분이었는데 실제 2호선 저녁 배차는 4~5분.

## 6. 열린 항목

### 6-1. 버스를 넣으면 무엇이 깨지나 ⭐

**엔진은 안 깨진다. 저장 방식이 깨진다.**

수도권 버스 정류장 약 5만 개. 노드가 741 → 51,000 이 되면:

| 방식 | 계산 | 결과 |
|---|---|---|
| 역→역 행렬 (지금) | 700 × 51,000 × 232슬롯 × 1B | **8.2 TB** ❌ |
| 역→격자 벡터 (500m) | 700 × 232슬롯 × 50KB | **8.1 GB** △ |
| 역→격자 벡터, 슬롯 3개 | 700 × 3 × 50KB | **105 MB** ✅ |

**슬롯 수가 곱셈의 주범이다.** 지금 232슬롯(10분 단위 × 양방향)은 지하철만이라
감당되는 숫자다. 버스가 들어오면 셋 중 하나를 골라야 한다.

1. 슬롯을 줄인다 — 피크만 10분, 평시 1시간 → 약 40슬롯 → 1.4GB
2. R2 같은 오브젝트 스토리지로 간다 — 8GB 는 문제없다 (GitHub Pages 1GB 로는 불가)
3. 격자를 성기게 — 1km 격자면 4배 줄지만 도보권 해상도를 잃는다

### 6-1b. 역 그래프 최신화 — 시도했고 막힌 지점 (2026-08-30)

2020년 그래프를 Wikidata(CC0)로 갈아보려다 **중단**했다. `tools/build_graph.py` 에
남겨 두었으니 이어서 하려면 거기서부터.

**확인된 것:** Wikidata 에 최신 노선이 전부 있다. GTX-A·신림선·별내선·대곡소사선·
신분당 신논현 연장·서해선·김포골드 — 검사한 7개 노선 모두 역이 빠짐없이 들어 있다.
신분당 연장을 넣으니 강남→여의도가 **31분 → 19분**으로 실제에 가까워졌다.

**막힌 것:** Wikidata 의 인접 관계(P197)가 **서비스 레벨을 섞어서** 담고 있다.
경부선에는 KTX 급 인접(서울–광명–천안)과 완행 인접(서울–남영–용산)이 함께 있어,
물리 노선을 운행계통에 병합하면 **지름길 간선**이 생기고 도달권이 낙관적으로 나온다.

물리 노선을 빼면 지름길은 사라지지만 이번엔 역이 누락된다(수원·건대입구).
운행계통 라벨만으로는 커버리지가 모자라서다. **둘 사이에 깨끗한 지점이 없었다.**

선로는 차수 2가 대부분이어야 정상인데:

```
2호선    {1:2, 2:47, 3:2}                 ✅
신분당    {1:4, 2:12}                      ✅
1호선    {1:6, 2:61, 3:16, 4:12, 5:2}     ❌ 지름길
경의중앙  {1:6, 2:35, 3:14, 4:10, 5:4, 6:1} ❌ 지름길
```

**다음 수 (권장 순):**

1. **KTDB GTFS** — 진짜 해법. 버스까지 한 번에 해결되므로 [6-1](#6-1-버스를-넣으면-무엇이-깨지나-)과 묶어서 하는 게 낫다
2. 2020 GML 유지 + 신규 노선만 손으로 추가 (약 40역). 통제 가능하지만 수작업
3. Wikidata 노선별 수작업 정리. 확실하지만 오래 걸린다

**중요:** 운영 그래프는 건드리지 않았다. 검증된 정확도(편향 −0.9분 / ±7분 89%)가
그대로다. 최신 노선이 빠진 것보다 지름길로 틀린 값을 내는 게 나쁘다고 판단했다.

### 6-2. 오픈소스 엔진의 리소스 걱정은 대체로 오해다

R5/OTP2 가 10~16GB 를 먹는 건 **OSM 도로망 그래프**를 상주시키기 때문이고, 그건
라이브 질의를 받을 때 이야기다. 우리 구조에서는:

- 엔진이 **월 1회 배치에서만** 돈다. 런타임 상주 메모리 0
- 도보를 직선거리 원으로 근사하는 한 **OSM 그래프 자체가 필요 없다** — 메모리를
  가장 많이 먹는 부분이 통째로 빠진다

즉 "엔진이 무거워서 못 쓴다"가 아니라 **"무거운 걸 언제 돌리느냐"** 의 문제였고,
그건 [ADR-1](#adr-1-런타임에-라우팅-엔진을-돌리지-않는다) 에서 이미 답이 나와 있다.

### 6-3. GTFS 를 안 받기로 했다 (2026-09-03) → 직접 만들기로 뒤집힘 (2026-09-07)

> **뒤집힘.** 아래는 지하철만 다룰 때의 판단이고 그 범위에선 맞다. 버스를 넣기로
> 하면서 "받지 않는다"가 "**직접 만든다**"로 바뀌었다 — [ADR-22](#adr-22-없는-gtfs-를-기다리지-않고-만든다-2026-09-07) 를 볼 것.
> 이유는 같다(3년 묵은 데이터를 못 쓴다). 결론만 반대다.

**당시 결론: KTDB GTFS 는 받지 않는다.** 기준시점이 2023-03 이라 지금 시점에 3년 반이 묵었고,
최신화가 이 프로젝트의 1순위 부채인데 그걸 해결하지 못한다.

**그리고 우리 구조상 GTFS 의 `stop_times`(진짜 시간표)는 애초에 안 쓴다.**
[ADR-6](#adr-6-합성-시간표를-쓰되-탐색은-진짜-시간표만-안다) 에서 이미 배차간격으로 시간표를
합성하고 있다. 필요한 건 넷뿐이다 — 정류장 좌표 / 노선별 정류장 순서 / 시간대별 배차간격 /
구간 소요시간.

앞의 셋을 **상시 갱신되는 TAGO API 가 그대로 준다**(2026-09-03 문서 확인):

| 필요한 것 | API | 필드 |
|---|---|---|
| 정류장 좌표 | 버스정류소정보 `15098534` | `nodeid` `gpslati` `gpslong` |
| 노선별 정류장 순서 | 버스노선정보 `15098529` | `getRouteAcctoThrghSttnList` |
| 첫차·막차·배차간격 | 〃 `getRouteInfoIem` | `startvehicletime` `endvehicletime` `intervaltime` `intervalsattime` `intervalsuntime` |
| 지하철 역·시간표 | 지하철정보 `15098554` | 역별 시간표 조회 |

배차간격이 **필드로 그대로 온다.** `TimetableBuilder` 에 바로 꽂히는 모양이고,
2023년 GTFS 를 파싱해 배차를 역산하는 것보다 정확하고 최신이다.
덤으로 **노선별 첫차·막차**가 오므로 보류했던 막차 레이어가 풀린다.

**빠지는 것은 하나 — 버스 구간 소요시간.** GTFS `stop_times` 가 주던 유일한 값이다.
(a) 거리 ÷ 표정속도 + 시간대 배율(철도에 쓰는 방식) 로 시작해 카카오 버스 경로와 대조하고,
편차가 크면 (b) 도착정보 API `15098530` 을 일주일 샘플링해 실측으로 간다.

⚠️ TAGO 는 **별도 활용신청**이 필요하다. 실거래가용 키로 부르면
`SERVICE_KEY_IS_NOT_REGISTERED_ERROR` 가 난다(확인함).

## 7. 개발하며 잡은 버그와 교훈

기록해두는 이유는, 같은 종류가 또 나오기 때문이다.

### 7-1. 깊이 들어간 사례 넷

표 한 줄로는 "어떻게 찾았나"가 안 남는다. 진단 과정이 결론보다 오래 쓸모 있었던 것만 따로 적는다.

---

#### ① 노선이 141조각으로 갈라졌다 — 스키마를 가정한 대가

**증상.** 그래프를 만들고 노선을 이어 붙였는데 **체인이 141개** 나왔다. 수도권 전철은
23개 노선이니 자릿수가 틀렸다. 그런데 도달권 자체는 그럴듯하게 나왔다 — 오히려 **실제보다 빨랐다.**

**왜 어려웠나.** 결과가 "명백히 틀린" 모양이 아니었다. 강남에서 40분이면 어디까지, 하는 그림이
그럴듯하니 눈으로는 안 잡힌다. 체인 개수를 세는 진단을 넣지 않았으면 몰랐을 것이다.

**어떻게 좁혔나.**
1. 체인 개수 141을 이상 신호로 잡고, 체인 길이 분포를 찍었다 → 길이 1~2짜리가 대부분
2. 그 짧은 체인들의 간선을 덤프했다 → `line_no` 가 **빈 문자열**
3. 그 간선들의 양끝 역 이름을 봤다 → **전부 같은 이름**

**원인.** GML 에 선로 간선과 **환승 통로**가 같은 `edge` 로 들어 있었다. 환승 통로는
`line_no` 가 비어 있는데, 나는 모든 `edge` 를 선로로 읽고 있었다. 그래서 환승이
"열차를 타는 것"으로 처리돼 대기시간 없이 0초에 갈아탔다.

**고친 방법.** `line_no` 가 빈 간선 140개를 선로에서 제외하고, 같은 역의 승강장끼리
거리 기반으로 환승 간선을 새로 만들었다(`overhead + meters / 1.2`). 체인 141 → **29개**.

**교훈.** 데이터를 눈으로 보기 전에 스키마를 가정하지 말 것. 그리고 **"그럴듯한 결과"는
검증이 아니다.** 자릿수를 세는 값싼 진단 하나가 없었으면 이 버그는 끝까지 남았다.

---

#### ② 강남역 08:00 에 한 정거장이 7분 — 도구를 만들어 잡았다

**증상.** 카카오맵과 대조하니 전체적으로 우리가 느렸다. 특정 구간이 아니라 **거의 전부**가
2~5분씩 느렸고, 특히 출근 시간대가 심했다.

**왜 어려웠나.** 숫자만 보면 "배차간격 추정이 대충이라 그렇겠지"로 넘어가게 된다.
실제로 처음엔 배차 표를 손으로 조정해봤고, 맞는 것 같다가 다른 구간이 틀어졌다.
**증상이 전역적이라 원인을 국소화할 수가 없었다.**

**어떻게 좁혔나.** 추정을 멈추고 `--mode diag --explain 강남>홍대입구 --at 08:00` 을 만들었다.
탐색이 고른 경로를 역·노선·시각으로 한 줄씩 출력하는 진단이다. 찍어 보니:

```
강남 08:00 → 역삼 08:07   ← 한 정거장에 7분?
```

08:00 출근 피크(배차 3분)인데 대기가 6분 이상 붙었다. 시간표를 덤프해 보니 강남역의
출발시각이 `06:20, 06:26, 06:32…` — **06:20 대의 7분 배차가 08시까지 그대로 이어져** 있었다.

**원인.** 시간표를 노선 **시작점 기준**으로만 생성했다. 시작역에서 배차를 맞추고 이후 역은
소요시간만 더했으니, 중간역의 출발시각 위상이 실제와 어긋난다. 서비스 시간대가 바뀌어도
그 체인은 처음 배차를 물고 갔다.

**고친 방법.** 역마다 **위상 정렬**을 한다. 누적 소요시간을 그 시간대의 배차로 나눈 나머지를
위상으로 잡고, 해당 서비스 구간의 시작 시각에서 그 위상에 맞는 첫 출발을 찾는다.

```kotlin
val phase = Math.floorMod(cumulative, headway)
var t = period.startSec + Math.floorMod(phase - period.startSec, headway)
```

**결과.** 편향 **+3.4분 → −0.9분**, ±7분 이내 83% → **89%**.

**교훈.** 숫자만 보면 왜 틀렸는지 알 수 없다. **경로를 출력하는 진단 도구를 먼저 만드는 것**이
추정으로 파라미터를 흔드는 것보다 빨랐다. 그 도구는 이후에도 계속 썼다.

> 부기: 20~23시 배차를 7분 → 5분으로 고친 것은 이 18쌍 표본에 맞춘 게 아니라
> **실제 2호선 야간 배차가 4~5분**이라는 독립 근거로 바꿨다. 표본에 맞추면 그건 과적합이지 검증이 아니다.

#### ③ 상봉동 원룸 "1.2억 / 월 29만" — 코드는 정상이었다

**증상.** 동네 시세를 지도에 올렸더니 상봉동 원룸이 **보증금 1.2억에 월세 29만**으로 나왔다.
그런 매물은 존재하지 않는다.

**왜 어려웠나.** **버그가 아니었다.** 파이프라인은 성공을 반환했고, 입력 데이터도 정확했고,
중위값 계산도 맞았다. 예외도 경고도 없다. 단위 테스트를 아무리 짜도 안 잡힌다 —
무엇이 맞는 값인지 코드가 알 수 없기 때문이다.

**어떻게 좁혔나.** 아는 동네를 몇 개 꺼내 실제 시세와 대조하다가 발견했다. 원인 추적은
집계 코드를 다시 읽는 것으로 충분했다.

```kotlin
"wolseDeposit" to median(wolse.map { it.amountManwon }),   // 보증금 중위
"wolseMonthly" to median(wolse.map { it.monthlyManwon }),  // 월세 중위
```

**원인.** 보증금 중위값과 월세 중위값을 **각각 뽑아서 짝지었다.** 반전세 몇 건이 보증금
분포를 끌어올리는 동안 월세 분포는 그대로였다. 두 주변부 통계를 합치면 **존재하지 않는 개체**가 만들어진다.

**고친 방법.** 환산월세(`월세 + 보증금 × 5.5% ÷ 12`)로 거래를 한 줄로 세워 중위를 구하고,
그것을 다시 **보증금 1,000만원 기준 월세**로 되돌린다. 처음엔 "가운데 있는 실제 거래 한 건"을
그대로 쓰려 했는데, 그 한 건의 보증금 구조가 우연이라 동네끼리 비교가 안 됐다
(화곡동 중위 거래가 8,130/40 이면 그 동네가 그렇다는 뜻이 아니다). 기준을 통일해야 비교가 된다.

**결과.** 상봉동 1.2억/29 → **1,000/85**. 역삼동 1,000/98, 신림동 1,000/73 —
실제 시세와 맞고 동네끼리 직접 비교된다.

**교훈.** **주변부 통계를 각각 요약해 합치면 존재하지 않는 개체가 만들어진다.**
합쳐야 할 때는 개체를 먼저 고르고 그 개체의 값을 읽어야 한다.
그리고 이런 오류는 테스트가 아니라 **도메인 지식으로만** 잡힌다 — 아는 동네 다섯 개를
꺼내 보는 것이 어떤 단위 테스트보다 빨랐다.

#### ④ 역 그래프 최신화 — 시도하고, 안 되는 걸 인정하고, 되돌렸다

**동기.** 역 데이터가 2020년이라 GTX-A·신림선·별내선·신분당 신논현 연장이 없다.
Wikidata(CC0)에 최신 노선이 다 있는 걸 확인했고, 신분당 연장을 넣어보니
강남→여의도가 **31분 → 19분**으로 실제에 가까워졌다. 되는 줄 알았다.

**막힌 지점.** Wikidata 의 인접 관계(P197)가 **서비스 레벨을 섞어서** 담고 있었다.
경부선에는 KTX 급 인접(서울–광명–천안)과 완행 인접(서울–남영–용산)이 함께 있다.
물리 노선을 운행계통에 병합하면 **지름길 간선**이 생겨 도달권이 낙관적으로 나온다.

선로 그래프는 차수 2가 대부분이어야 정상인데, 차수 분포를 찍으니 바로 드러났다:

```
2호선    {1:2, 2:47, 3:2}                  ✅ 정상
신분당    {1:4, 2:12}                       ✅ 정상
1호선    {1:6, 2:61, 3:16, 4:12, 5:2}      ❌ 지름길
경의중앙  {1:6, 2:35, 3:14, 4:10, 5:4, 6:1}  ❌ 지름길
```

물리 노선을 빼면 지름길은 사라지지만 이번엔 **역이 누락된다**(수원·건대입구).
운행계통 라벨만으로는 커버리지가 모자랐다. **둘 사이에 깨끗한 지점이 없었다.**

**결정: 되돌렸다.** 운영 그래프는 건드리지 않았다. 검증된 정확도(편향 −0.9분 / ±7분 89%)가
그대로 남았고, 작업물은 `tools/build_graph.py` 에 "⚠️ 미완성" 으로 표시해 남겼다.

**교훈.** **최신 노선이 빠진 것보다 지름길로 틀린 값을 내는 게 나쁘다.**
"더 새로운 데이터"가 항상 "더 나은 데이터"는 아니다. 그리고 차수 분포처럼
**구조가 스스로 드러나는 지표**를 찍어보는 습관이 이 판단을 가능하게 했다 —
그게 없었으면 지름길이 섞인 채로 배포했을 것이다.

> 이 문제의 진짜 해법은 TAGO 지하철정보 API 다(→ [6-1b](#6-1b-역-그래프-최신화--시도했고-막힌-지점-2026-08-30)).
> 운행계통이 그대로 들어 있어 물리 노선과 섞이지 않는다.

### 7-3. 정리

**가장 큰 교훈:** 화면을 봐야만 보이는 버그가 있다. TDZ 와 `setData` 는 타입체크도
헤드리스 검증도 통과했고, 실제 브라우저 화면을 열어보고서야 잡혔다.

**두 번째 교훈(2026-08-31):** 데이터도 눈으로 봐야 한다. "상봉동 원룸 1.2억/29만"과
"강남역 3km 안 백화점 879개"는 둘 다 코드가 정상 동작한 결과였다. 파이프라인이 성공을
반환한다고 값이 맞는 건 아니다. **아는 동네 몇 개를 꺼내 실제 시세와 대조하는 것**이
어떤 단위 테스트보다 빨리 잡아냈다.

**원자료를 남겨두는 것의 값어치도 이날 증명됐다.** 집계 방식을 두 번 바꿨는데, 원자료
JSONL 이 있어서 45분짜리 수집 대신 30초짜리 재집계로 끝났다. 한 번은 수집 잡이 도중에
죽었는데도 그 전에 쓰인 원자료로 복구했다.

## 8. 실행

```bash
# 행렬 생성 (약 3초)
./gradlew :builder:run --args="--gml data/raw/metro_graph.gml --out web/public/data --step-min 10"

# 웹
cd web && npm install && npm run dev
```

진단·검증 도구:

```bash
# 그래프 구조 + 대표 구간 소요시간 + 실제 선택 경로
./gradlew :builder:run --args="--mode diag --gml data/raw/metro_graph.gml --explain 강남>홍대입구 --at 08:00"

# 외부 서비스 대조
./gradlew :builder:run --args="--mode compare --gml data/raw/metro_graph.gml --reference tools/reference-kakao.json"

# 브라우저 없이 도달권 SVG (계산이 틀린 건지 화면이 틀린 건지 가를 때)
./gradlew :builder:run --args="--mode render --gml data/raw/metro_graph.gml --from 강남 --at 08:40 --budget 40 --out data/out/reach.svg"
```

버스·GTFS:

```bash
# 수집 (재개 가능 — 이미 받은 건 건너뛴다)
./builder/build/install/builder/bin/builder --mode bus        # 경기 (TAGO)
./builder/build/install/builder/bin/builder --mode seoulbus   # 서울
./builder/build/install/builder/bin/builder --mode seoulspeed # 구간 속도 스냅샷 1회

# GTFS 생성 + 검사
./builder/build/install/builder/bin/builder --mode gtfs
./builder/build/install/builder/bin/builder --mode gtfscheck
```

위 전부를 묶어 하루 5회 자동 실행한다:

```powershell
# 등록 상태 확인
Get-ScheduledTask -TaskName 'chulsegwon-collect' | Format-List TaskName, State
Get-Content data/logs/progress.csv          # 회차별 지표
Get-Content data/logs/collect-*.log -Tail 30
```

> ⚠️ `tools/collect.ps1` 은 **UTF-8 BOM** 으로 저장해야 한다. PowerShell 5.1 이
> BOM 없는 파일을 CP949 로 읽어서 한글 주석이 깨지고 구문 오류가 난다.

> ⚠️ 인자 파서가 `--key value` 쌍만 받는다(`args.chunked(2)`). `--check` 같은
> 단독 플래그는 조용히 무시되므로 `--check true` 로 써야 한다.
